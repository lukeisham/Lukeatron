# Rhetoric

An offline, in-browser reference app that shows rhetorical devices organised across three independent hierarchies — Category, Form and Function — as a clean, re-organisable list. Luke uses it during teaching preparation: sorting, reading a definition and examples, and printing or copying a chosen group. Each device has a definition, examples, a popularity score and an AI-confidence rating. Under **Grammar**, Luke makes his own grammar labels (each with an explanation, up to four levels deep) and files devices under them with a type-ahead box (see "Grammar group" under Cross-app behaviour). The **Index** group lists every real quote, by first line, source or date. Under **Topical**, Luke makes his own Type labels (up to four levels deep, like Grammar's), drags devices onto them (a device may sit under several Types) and drags Types and devices into his own order; that arrangement and the Grammar labels with their devices are the only things the app lets him change.

## Launch / restart
- Double-click `Start Rhetoric.command`, or run `python3 server.py` from this folder and open `http://127.0.0.1:8794`.
- To restart: close the Terminal window (or press Ctrl-C) and launch again. If it reports the port is in use, an earlier Rhetoric is still running.
- To rebuild the database from scratch, see `schema.sql` and the `seed/` modules (run from this folder with `python3 -m seed.<module>`). A rebuild discards Luke's Topical Types and placements and his Grammar labels and placements, so copy `rhetoric.db` first. To add the Topical tables to an older database without rebuilding it, run `sqlite3 rhetoric.db < schema.sql` (it only creates what is missing). To add the example `attribution` column to an older database, run `python3 -m seed.add_example_attribution`; it fills the tags from `seed/devices.json`, can be run twice safely, and leaves Topical Types alone. `python3 -m seed.add_quote_date` does the same for the `quote_date` column. `python3 -m seed.add_grammar_placements` brings an older database's grammar tables up to the editable Grammar group (a `position` column, the `grammar_placements` table, the retired slot tables dropped); it refuses while those retired tables hold rows and can be run twice. `python3 -m seed.add_label_tables` adds the `tables_json` column (label tables) to both tree tables of an older database; it can be run twice.

## Cross-app behaviour
**Display order.** Wherever a device is shown (list, Compare, Copy, Print), the order is device name, description, AI example, real quote. Standing rule from Luke (2026-10-05): do not change it. `app/render.js` draws the name, definition, Grammar explanation and examples in that order, and `items.py` (`_device_map`) sorts a device's examples so the AI example comes before its real quote whatever their row ids; `tests/test_items.py` covers it.

**Between apps.** Home launches Rhetoric: its `catalog.json` entry runs `server.py` from this folder's root on port 8794. Moving or renaming `server.py`, or changing the port, breaks that tile. The port is also fixed in `server.py` and `Start Rhetoric.command`. Rhetoric reads nothing from another app and no other app reads its data.

**Between files.**
- `schema.sql` → `items.py`: table and column names. `nodes` (one table, `hierarchy` in category|form|function, `parent_id`); `devices` (`form_node_id`, `function_node_id`, `popularity` 0–100 required, `topical_rank` nullable and Luke-set only, `ai_confidence_rating` high|medium|low default low, `flipside_of`); `device_categories` (1+ per device); `examples`. `examples` (`body`, plus `attribution`: the person an example's words are credited to, `Unattributed` when none is recorded; never null). `topical_types` (unique case-blind `name`, `position` = display order) and `topical_placements` (`type_id`, `device_id`, `position` = order within the Type; one row per Type a device sits under). A rename breaks `/api/items` with a 500. `topical_rank` is not read by the app; Types and placements order the Topical view.
- `items.py` → `server.py` → `app/`: `GET /api/items` returns `trees` (one per hierarchy, device leaves as ids) plus a flat `devices` map, each device sent once. Every sort, search and filter runs client-side on that single payload. `server.py` checks the API route before serving `app/` as static files, and returns 503 if the database cannot be opened (`app/api.js` treats any non-OK response as "could not load"). The server opens the database read-only for `GET`; the only writes it accepts are the Topical and Grammar routes below, and every other POST, PUT, PATCH or DELETE gets 405.
- Topical writes: `server.py` (routing and the origin gate) → `topical.py` (the only SQL that writes) → `items.py` (rebuilds the tree to answer with). Routes: `POST /api/topical/types` (`name`, optional `parent_id`), `PUT`/`DELETE /api/topical/types/<id>` (rename, delete), `PUT /api/topical/types/<id>/position` (move a Type to `index`; an optional `parent_id` also moves it, with everything beneath it, under that Type, or to the top level when 0), `PUT`/`DELETE /api/topical/types/<id>/devices/<device id>` (place, remove; a `PUT` with an `index` also places the device at that spot, which is how a device is moved within a Type). Each answers `{topical: <fresh Topical tree>}`, and `app/api.js` hands that to `setEditableTree` in `state.js`, so the screen only shows what was saved. A write must carry this server's own `Host`, any `Origin` must match it, and a body must be `application/json`; otherwise 403 or 400. Writes touch only the two `topical_*` tables (and, for the Grammar routes, the two `grammar_*` tables), never the devices or the three seeded hierarchies.
- The Topical tree travels as `trees.topical`, the same shape as the other trees: one node per top-level Type, each with its sub-Types first and then its own devices, then a derived **Unsorted** node (id 0, `UNSORTED_ID` in `topical.py` and `state.js` must agree) holding every device with no Type at any level. **Nesting (Luke, 2026-10-06):** Types nest up to four levels deep (`MAX_DEPTH` in `topical.py` and `grammar.py`, `MAX_LABEL_DEPTH` in `state.js`: all three must agree; a fifth is refused with 400); sibling names are unique case-blind (409, enforced by `idx_topical_types_sibling_name` as well as in code); a Type with sub-Types cannot be deleted (409, so none are lost silently); a Type can be dragged to another parent or to the top level (see Drag and drop); a move that would put it under itself or its own sub-Types, or push its deepest sub-Type past four levels, is refused with 400, and one onto a sibling's name with 409. Table `topical_types` carries `parent_id`; `python3 -m seed.add_topical_nesting` rebuilds an older flat table (kept every Type as top-level). On screen the **Add Type** form has an "At the top level / Under …" menu, filled by `fillParentPicker` in `main.js` (the same function fills Grammar's), listing only Types with room for a child. Node ids overlap other hierarchies, so an open heading is keyed `hierarchy:id` (`openKey` in `state.js`). Topical is not part of the no-group search.
- Drag and drop: `render.js` marks Topical device rows and each real Type's heading row `draggable`, and each real Type `data-droppable`; `drag.js` listens on the list, reports what was dropped where, and `main.js` turns that into a save, using `order.js` for the index (counted on the saved tree, not on what a search leaves on screen). A device on a Type's heading goes last; a device on another device row goes before or after it (top or bottom half); a Type or label on another Type or label of its group goes by where on the heading it lands: the top quarter puts it just before that heading and the bottom quarter just after it (both under that heading's parent, so this is how a label changes level), and the middle, or anywhere over what is beneath the heading, puts it inside it, last among its sub-labels (`zoneOf` in `drag.js`, `movedTo` in `main.js`). It cannot be dropped onto itself or anything beneath it. The server decides whether the move fits (`labeltree.move`, shared by `topical.py` and `grammar.py` along with the depth and sibling-name rules); a move it refuses says so in the group's status line. Dropping a device copies, so it also stays under its other Types; the × on a row removes it from that Type only. Unsorted is always last and cannot be moved or dropped onto. The same code serves the Grammar group: every label is draggable and droppable, `drag.js` reports the group (`hierarchy`) with each drop, and a label is never dropped across groups.
- **Grammar group.** Luke's own grammar labels, edited in the app the way Topical is; the slots, examples and summaries the group once had (Grammar function and Grammar form) were dropped on 2026-10-05, at Luke's choice. A label is a grammatical term with an explanation (`definition`, required, up to 300 characters), up to four levels deep (`MAX_DEPTH` in `grammar.py` and `MAX_LABEL_DEPTH` in `state.js` must agree; a fifth is refused with 400); sibling names are unique case-blind (409), and a label with sub-labels cannot be deleted (409, so none are lost silently). A device is filed under any number of labels at any level, so it can sit under a label and under one of its sub-labels. Tables: `grammar_labels` (`parent_id`, `name`, `definition`, `position` among siblings) and `grammar_placements` (`label_id`, `device_id`, `position`, one row per label a device sits under; removed with the label by `ON DELETE CASCADE`). Writes: `server.py` (same gate as Topical) → `grammar.py` (the only SQL that writes them) → `items.py` (`load_grammar` answers with the fresh tree). Routes: `POST /api/grammar/labels` (`name`, `definition`, optional `parent_id`), `PUT`/`DELETE /api/grammar/labels/<id>` (edit name and explanation, delete), `PUT /api/grammar/labels/<id>/position` (move to `index`; an optional `parent_id` also moves it, with everything beneath it, under that label, or to the top level when 0), `PUT`/`DELETE /api/grammar/labels/<id>/devices/<device id>` (file, remove; a `PUT` with an `index` also moves). Each answers `{grammar: <fresh tree>}`. The tree travels as `trees.grammar`, the same shape as the others: each label's sub-labels first, then its devices, every label kept even when empty; there is no derived "no grammatical term" heading, and a group with no labels is an empty list, which the screen reports as "No labels yet. Add one above, then add devices to it." On screen (`index.html`'s `#grammar-bar`, shown only in this group): an **Add label** form (name, explanation, and an "At the top level / Under …" menu limited to labels with room for a child) and an **Add device** form, a type-ahead box (`app/picker.js`: the drop-down narrows as Luke types, by the same matching as the search box, so the **Fuzzy match** option applies; arrows and Enter choose, a second Enter adds; a name typed out in full also counts) and a menu of every label. A label's own **Add device** button aims that form at it; **Edit** (two prompts: name, then explanation), **Delete** and the × on a device row work as Topical's do; a device already under the chosen label is reported, not added twice. The label's explanation is drawn beside its name; both follow the `*italic*` star rule of examples (`inlineSpan` in `render.js`; every tree heading uses it, and Copy, the pickers and the button labels drop the stars). Like Topical, the group is not part of the no-group search, and the older `seed/load_grammar.py` and its files were retired (copies in `Archive/Rhetoric-grammar-slots-retired-2026-10-05/`, including a draft label tree).
- **Label tables (Luke, 2026-10-06).** A Grammar label or a Topical Type, at any of its four levels, holds up to 5 tables. Stored in a `tables_json` column on `grammar_labels` and `topical_types` (a JSON list, written only through `grammar.set_tables` / `topical.set_tables`, which share `labeltables.py` for the shape and limits); each node in `trees.grammar` and `trees.topical` carries `tables` (an empty list when none; the derived Unsorted always has none). A table is `{caption, colHeads, rowHeads, cells}`: `cells` is the whole grid as drawn, rectangular; with `colHeads` its first row is the column headings, with `rowHeads` its first column is the row headings (both: the top-left cell is the corner). Limits (`labeltables.py` and `app/tablegrid.js` must agree): 5 tables, 20 rows, 8 columns, 200 characters a cell, 120 a caption. Routes: `PUT /api/grammar/labels/<id>/tables` and `PUT /api/topical/types/<id>/tables`, body `{tables: [...]}` replacing the whole list, answering with the fresh tree; the body limit is larger (`MAX_TABLES_BODY_BYTES`) and `_as_tables` in `server.py` judges it through `labeltables.clean`, so a malformed table is a 400. On screen: `render.js` `tableItem` draws each as a real `<table>` first under its label (headings are `<th scope=col|row>`, bold in `labeltable.css`; cell text goes through `inlineSpan`, so the star rule applies and nothing is markup); a label's **Add table** button and each table's **Edit table** button open `#table-dialog` (`app/tableeditor.js`; pure grid logic, including pasting spreadsheet text, in `app/tablegrid.js`), and `main.js` `editTable` saves the label's whole list. Tokens `--font-size-table-min` and `--table-char-width` are in `tokens.css`. The tables go with their label when it is deleted; moving or editing a label keeps them.

## AI confidence rating: rubric
`ai_confidence_rating` is a stored value, never computed at run time. It is set once per device in `seed/devices.json`, then copied unchanged through `load_devices.py` → `rhetoric.db` → `items.py` → `state.js` → `render.js` (badge) and `main.js` (toggle). Only the seed step may change it, so this rubric is applied there. `seed/confidence-scoring.md` records which tests each device failed and why.

**What the rating claims** (as `schema.sql` words it): the AI's confidence that the device's definition, example and categorisation are accurate *together*. Score three yes/no tests, then count the passes.

| Test | Passes when |
| :--- | :--- |
| **1. Definition** | It has one settled meaning (a term with rival senses, e.g. Adnomination, fails), AND either it is named in 2 or more distinct sources (the four scraped lists plus the reference sources counted in `seed/popularity.json`; Wikipedia never counts), OR a published handbook, primary text or scholarly paper that is not already a counted source gives the same sense. Name that work, with a locator, in `seed/confidence-scoring.md`. Commercial and hobby sites do not qualify. A description whose wording rests on Wikipedia alone fails this test, even if listed sources name the device. |
| **2. Example** | At least one example exists, and a reader who did not know the device's name could identify it from the example alone. For a fallacy, the example visibly commits the error. |
| **3. Categorisation** | Its Form, Function and Category placements each follow `seed/classification-criteria.md` directly. Fails if any placement needed a judgement call between close nodes or stretches a node's definition. |

| Passes | Rating | Reads as |
| :--- | :--- | :--- |
| 3 | `high` | Safe to teach from as it stands |
| 2 | `medium` | Worth a check before relying on it |
| 0–1 | `low` | A draft; verify before use |

**Rules of use**
- A device that fails Test 1 can never be `high`, because nothing outside the AI vouches for its definition.
- A description sourced only from Wikipedia (Definitions, step 2, tier 2) fails Test 1, which lowers the label: at most `medium`. Naming in two lists does not rescue it, because those lists did not supply the wording. Record "Wikipedia only" for the device in `seed/confidence-scoring.md` and re-score it in the same change.
- A Flipside is rated on its own. Every Flipside label is coined for this app and appears in no source, so Flipsides fail Test 1 and top out at `medium`.
- Never leave a device unrated: an unscored device stays `low` (the schema default).
- When a device is edited (new definition, example or placement), re-score it in the same change and update `seed/confidence-scoring.md`.

**Standing caveats.** The labels are stored in `seed/devices.json` and `rhetoric.db`. The Test 1 check uses Silva Rhetoricae's citation lists plus a few scholarly works; those citations are second-hand and the primary texts were not read. Devices that fail Test 1 are listed in `seed/confidence-scoring.md` with the reason. Parataxis is `high` by Luke's decision and fails the tests on paper (see `seed/confidence-scoring.md`). Tests 2 and 3 are the AI's judgement and have not been checked by Luke.

## Examples and quotes: how to find and add them
These rules apply to any device; Flipsides have their own rule (step 5).

1. **Prefer a real quote.** The scope is as wide as can be: anywhere a quote can be found and verified, including non-fiction, fiction, film, poetry, speeches, history, things fictional characters say, folk sayings, riddles and songs. A device keeps exactly one real, credited quote and exactly one AI-generated (constructed) example, side by side (see "Constructed examples" below). Add the quote beside the constructed example. If the device already has a real quote and the new one is a cleaner match, the new one replaces the old real quote, once the new one has been checked. The constructed example is never removed because a real quote was found, and a real quote is never removed to make room for a constructed one. Do not invent a quote to fill the gap.
2. **It must match the device cleanly.** Test 2 (see the rubric) is the floor: a reader who did not know the device's name could identify it from the quote alone. Above that floor, aim for the best match available:
   - **Whole definition.** Every part of the definition is in the quote, doing the job the definition names. A quote that contains a word or a related trick but not the defining move does not count.
   - **Main trick.** The device is what the quote is built on, not something incidental that happens to appear in a longer sentence.
   - **Stands alone.** It works without the surrounding text. At most one short parenthesis may name the quote's moving parts (for example which sense of a word is meant), but the parenthesis must never supply the device itself. If the reader needs a note about the author's name, the age or a pun in another language to see it, it fails.
   - **Cleanest instance.** Among candidates, take the most standard, handbook-style instance over a more famous but looser one.
   - **Fallacies and Flipsides.** A fallacy quote commits the error as an argument and does not merely describe it. A Flipside quote shows the legitimate use, with its evidence or reasoning visible.
   - **Check the fallacy's definition first.** Search results and example lists often put the wrong label on a fallacy. Before judging a quote against a fallacy or Flipside, check the fallacy's definition in a second named source (for example the Internet Encyclopedia of Philosophy, the Stanford Encyclopedia of Philosophy or Purdue OWL) and confirm it agrees with the definition in the database. Never rely on a search summary that calls something an example of the fallacy.
   - **No swear words or sexual content.** Do not use a quote that contains swear words or sexual content, even when it is otherwise the best match. Do not clean it up either, because an altered quote is no longer a verified quote; choose another. Other offensive material, such as hostile views or propaganda, is allowed where it is the best verified match, and the `app-decisions.md` row should say so.
   - **Shorter is better.** Use the shortest passage that still meets every point above: cut lead-in and trailing sentences, and join non-adjacent parts with an ellipsis. Between two quotes that match equally well, take the shorter.
   - **Several senses.** If a device has more than one sense or kind, the quote shows one of them, and the parenthesis says which.
   - **When no clean match is found.** Search properly first (several works and kinds of source). Only then add the closest quote, and flag it as a loose fit (step 8). A loose quote is a placeholder, and the cleaner quote replaces it when one turns up.
3. **Check it against a text before adding it.** Find the work itself (full text, an official transcript, or a reputable edition or scan) and confirm the wording, the speaker and a locator (chapter, scene, date). For plays, epics and books, use the numbering of the Project Gutenberg text. A search summary, a quotation site or memory is not a check. For a song, check the lyric against the recording's official lyrics or liner notes. For a folk saying, riddle or other common saying, which has no single author, show that it is common: it appears in at least two independent named collections or dictionaries of proverbs (or the equivalent), and give the earliest attested form found. If a known author or origin turns up, credit that person instead. If only an anthology excerpt or a transcript on a secondary site can be found, say so in the `app-decisions.md` row.
4. **Translations.** Prefer a named translator whose wording you have read, in the body (for example "trans. Yonge"). If no such translation can be used and the device exists in another language (the figure depends on that language, such as Latin case endings), an AI translation is fine, provided you have verified that the device really exists in that language: find the original text, and a source that names the figure for that language. Say in the parenthesis that the English is by Claude (AI). Never translate it yourself and credit someone else. Note any spelling that was modernised.
5. **Flipsides.** The aim is a real, verified quote for every Fallacy Flipside, however long finding them takes. Every Flipside label is coined for this app, so no source gives a ready-made example, and each quote must show the legitimate use, not just the fallacy. A Flipside's constructed example stays, and the real quote is added beside it (step 1: one real quote and one constructed example per device). Say in the `app-decisions.md` row that the example is for a Flipside.
6. **Credit and date.** `attribution` is the person the words are credited to ("Winston Churchill"). For a fictional character's words in a book, play or poem, credit the author or writer and name the character in the example text; for a character in a film (or other screen work), credit the character by name ("Maximus"), because screenplay credit seldom says who wrote a line, and give the film and year in the closing parenthesis (Luke, 2026-10-05); for a song, credit the songwriter; for a folk saying, riddle or other verified common saying, use `Unattributed` and give the earliest source in the example text. The work and passage go in the example text, in a closing parenthesis, with titles in `*italics*`. Do not write "attributed to". Use `Unattributed` only when no credit is held (as with verified common sayings, folk sayings and riddles).
   **Date.** If it can be found quickly, record when the words were first said or published, as the optional `"date"` on the example in `seed/devices.json` (the database's `quote_date`): `YYYY-MM-DD` for a speech, broadcast, letter or dated article, `YYYY` for a book or poem. Do not search for it. Take it from the source already read for step 3, or from what the closing parenthesis already states, and give up after one quick look; an unknown date is left out, and the Index lists the quote as "Date unknown". Never guess, and never store an approximate date ("c. 1600"): the column accepts only a year or a full date. A year under 1000 is written with four digits (`0060` is AD 60) and a year BC with a minus sign (`-0935` is 935 BC, with no year 0); the Index shows them as "AD 60" and "935 BC" and groups them as "AD 60s" and "930s BC". Exception (Luke, 2026-10-05): for the books of the Bible, Shakespeare's plays and other ancient or medieval works, whose dates are scholars' estimates, store a single year and say in the `app-decisions.md` row that it is an estimate. Bible: conservative scholarship's date of writing. Plays: the composition year, not the First Folio's 1623; Sonnets: the 1609 printing. Other works: the date Wikipedia gives, and where it gives only a range, the midpoint of the best-attested one (*Beowulf*: the manuscript's AD 975 to 1025, so `1000`; the Code of Hammurabi: c. 1753 BC, so `-1753`). Use the date of the original, not of a translation, an edition or a later book that quotes it (a credit's "1937" for a translation or "1898" for the work that listed the quote is not the quote's date). A constructed example has no date.
7. **Where it is written.** Add the example to `seed/devices.json` and insert the row into `rhetoric.db` as well; do not rebuild the database, because a rebuild discards Luke's Topical Types. Copy both files to a dated folder in `Archive/` first (`Rhetoric-pre-<what>-<date>/`) and keep the JSON in its existing layout (one-space indent, no escaping of non-ASCII), so a diff shows only the new examples. If an example has a `"date"`, run `python3 -m seed.add_quote_date` as well: it writes the dates from `seed/devices.json` into the live database, matching by device name and example text.
8. **Say when the fit is loose.** If a quote falls short of any point in step 2, name the point in the `app-decisions.md` row (for example "the transition announces little about what follows") instead of leaving it unremarked.
9. **After the change.** Run the tests, log a row in `app-decisions.md` (devices, sources, any quote replaced, new example, credited and dated counts, backup folder), and re-score the device if the new example changes its Test 2 result.
10. **Finding devices that still need a quote.** Do not judge by the credit alone, because a real quote with an anonymous author (such as the *Rhetorica ad Herennium*) is stored as `Unattributed`. A device has a real quote when an example is credited **or** its closing parenthesis cites a work: an italic title, a date or locator, or "trans.". A constructed example's parenthesis only explains it. `python3 -m seed.quote_status` (run from this folder, read-only) lists the devices with no real quote, and `--draw 5 --seed 20261006` gives a repeatable random draw of five.

## Constructed examples: how to write them
A constructed example is one the AI writes itself. Every device has exactly one, and it lives alongside the device's one real quote (quote rules, step 1); it is not a stand-in that goes away when a real quote is found. It follows the same Test 2 floor. These rules apply to any device, Flipsides included.

0. **One per device.** Each device has exactly one constructed example. A device with none gets one written; a device with two keeps the one that best meets steps 1 and 2 below, and the other is removed only with Luke's say-so, because that deletes a stored example.

1. **Illustrate the definition exactly.** Write from the device's definition, and check that definition first if it has not been verified (Definitions, step 2). Every part of the definition must be visible in the example, doing the job the definition names. The example must be that device and no other, and a reader who did not know its name could identify it from the example alone.
2. **Put the part the device depends on in italics.** If the device turns on a particular word, syllable, letter, sound, word ending, word order or punctuation mark, wrap exactly that part in `*asterisks*` and nothing else; for example, the repeated opening letters in Alliteration (`*P*eter's *p*roud *p*ursuit`), the matching word-endings in Homoioteleuton, the word with two senses in a Pun, the repeated word where one clause ends and the next begins in Anadiplosis. Italicise the smallest piece the device actually depends on: a letter or syllable when the device works at that level, a whole word when it works at that level. Where the device depends on a structure that spans the sentence (a mirrored pair in Chiasmus), italicise each part of the structure. Where it depends on no particular piece (a fallacy whose whole argument is the error), use no italics. The app reads a single pair of asterisks as italics, so never nest them and never use a literal asterisk for any other purpose.
3. **Fallacies and Flipsides.** A fallacy example commits the error as an argument and does not merely describe it. A Flipside example shows the same move without the fault, with the evidence or reasoning visible (Definitions, step 7).
4. **One example, one device.** Do not let a second device carry the example. If the sentence also happens to contain another figure, either leave it unremarked or change the wording so that it does not.
5. **Self-contained and short.** It works without surrounding text. Use the shortest wording that still meets steps 1 and 2. At most one short closing parenthesis, which may name the moving parts or say which sense is meant, and which must never supply the device itself.
6. **Do not pass it off as a quote.** Credit it to no one and give it no date: `attribution` is `Unattributed`, there is no `"date"`, and the parenthesis names no work, no date and no locator, and never says "trans.". Write a word it glosses in plain quotation marks inside the parenthesis, never in italics ("the word \"own\" only adds emphasis"): `quotes.py` reads an italic, a digit or "trans." in the closing parenthesis as a citation and would list the example in the Index as a real quote. `seed.quote_status` treats a parenthesis that cites a work as a sign of a real quote, so a citation-shaped parenthesis on a constructed example would make the device look as if it already had a real quote and hide it from the list of devices still needing one.
7. **Clean content.** No swear words and no sexual content; choose different wording. English only; if the device depends on another language (case endings, a foreign pun), do not construct an example, because a real quote with a translation is the only valid one (quote rules, step 4).
8. **Check before writing it in.** Put the definition and the example side by side and tick each part of the definition against the example. Check the italicised parts against the device: letters and word endings by counting them, a repeated word by reading the sentence aloud. If any part is missing or extra, rewrite.
9. **Where it is written, and after.** Same as the quote rules, steps 7 and 9: add to `seed/devices.json` and the row in `rhetoric.db` (no rebuild), back up to a dated `Archive/` folder first, run the tests, log a row in `app-decisions.md`, and re-score the device if its Test 2 result changes. The constructed example stays beside the real quote. When a definition is edited, re-check its constructed examples against the new wording.

## Definitions: how to write and verify them
These rules cover the `definition` field of any device, Flipsides included, whenever a definition is written, rewritten or kept. They are the counterpart of the examples-and-quotes rules above and use the same sources and the same Test 1 as the rubric.

1. **What a definition says.** Plain English, one or two sentences: what the device is, and what it does to the reader or listener. It names the defining move, not an example, and uses no jargon it does not itself explain. Existing definitions run from 33 to 249 characters; stay in that range unless a second sense needs one more sentence.
2. **Check the sources whenever a definition is written, rewritten or kept.** The AI does not write a definition from memory alone. Where a source can be found, it reads what the sources say the device is, then writes (or compares) against it. Look in this order and stop at the first tier that gives a definition of the device:
   1. **The sources used for the AI confidence score (Test 1).** The reference sources counted in `seed/popularity.json` (Silva Rhetoricae, Purdue OWL, Stanford Encyclopedia of Philosophy, the University of Kentucky glossary and, for fallacies, the Internet Encyclopedia of Philosophy and LogicalFallacies.org), the four scraped lists of devices, and any published handbook, primary text or scholarly paper that names the device in the same sense (for example *Rhetorica ad Herennium*, Quintilian, Peacham, Puttenham, Lanham). Commercial and hobby sites do not qualify (as in Test 1).
   2. **Wikipedia, only if tier 1 gives no definition of the device.** Read the article's own definition. A definition taken from Wikipedia can shape the wording, but it never counts for Test 1 (Wikipedia never counts as a source there). A description resting on Wikipedia alone therefore fails Test 1 and lowers the AI confidence label (at most `medium`; see the rubric's rules of use), even if listed sources merely name the device. Record that the wording came from Wikipedia only, in `seed/confidence-scoring.md`, and re-score the device. Wikipedia may also still be used to find candidate works for tier 1.
   3. **Ask Luke, if neither tier gives a definition.** Say which sources were tried and ask him what the device means. Do not write a definition unaided, and do not invent a source.
3. **Check the source text, not a summary.** Open the entry or the passage and read it. A search snippet, an AI summary or memory is not a check. Note the locator (entry name, section, chapter or line).
4. **Compare the whole definition.** Put the database definition beside each source and call it one of four things: **agrees** (same sense, nothing claimed that the source does not), **narrower** (leaves out part of the source's sense), **broader** (claims more than the source), or **different sense** (the source means something else). Only *agrees* counts as verified.
5. **Rival senses.** If sources disagree, give the main sense first and name the other in one closing sentence, as Adnomination does. If the sources cannot be reconciled, keep the definition as it is and let the device fail Test 1 (no single settled meaning).
6. **When nothing can be checked.** A device that appears in no source (tiers 1 and 2 of step 2) has no definition to verify against: ask Luke, as step 2 says, and until he answers the device stays unchecked and fails Test 1. A Flipside is the exception: its label is coined for this app, so no source names it and there is nothing to ask. Its definition is checked against its fallacy's verified one (step 7). Never invent a source or cite one that was not read.
7. **Fallacies and Flipsides.** Verify a fallacy's definition in a second named source, as step 2 of the quote rules requires (the Internet Encyclopedia of Philosophy, the Stanford Encyclopedia of Philosophy or Purdue OWL).
   - **What a Flipside is.** The fallacy's own move, used without the fault: not a cleaned-up or different device. The move is still that move, and it keeps the fallacy's name; what changes is that it is not pejorative. An appeal to authority used well is still an appeal to authority (Appeal to Authority has the Flipside Expert Voice); Begging the Question has Shared Ground, and Genetic Fallacy has Provenance Probe. Every fallacy has exactly one Flipside. The Flipside labels are coined for this app, so no source names them and there is nothing to verify them against (step 6).
   - **What its definition must say.** Describe the same move the fallacy describes, then say what makes this use fair: the point where the fallacy deceives or overreaches, here done openly or within its limits (the authority is genuine and speaks within their field, the premise is stated openly, the origin really bears on reliability). Write it as an instruction to the speaker, as the existing ones do ("Cite a genuine expert...", "Trace a claim's origin when..."). The definition must not describe the fault itself.
   - **How to check it.** Take the verified definition of the fallacy and strip out only the fault. What is left must still be the same move, and a reader who dropped the word "fallacy" would still call it by the fallacy's name. If what is left is a different device, it is not a Flipside. Valid argument forms with their own entry (Modus Ponens, Argument from Expert Opinion and the others `seed/classification-criteria.md` sends to Inventio) are separate devices, not Flipsides.
   - **Its other fields.** It usually shares its fallacy's Form; its Function follows the effect of the legitimate use; it inherits its fallacy's popularity. Its examples show the legitimate use with the evidence visible (quote rules, step 2).
8. **When to change a definition.** Only when the check shows *narrower*, *broader* or *different sense*, or when two devices' definitions overlap in a way that confuses (for example Parataxis and Asyndeton). Make the smallest edit that restores agreement and keep the device's meaning. A definition that agrees is left alone, even if it could be phrased better.
9. **After an edit, re-check the rest of the device.** The examples must still show the new wording (Test 2) and the placements still follow `seed/classification-criteria.md` (Test 3). Re-score the device in the same change.
10. **Where it is written.** Change `seed/devices.json` and update the row in `rhetoric.db` as well; do not rebuild the database, because a rebuild discards Luke's Topical Types. Copy both files to a dated folder in `Archive/` first (`Rhetoric-pre-<what>-<date>/`) and keep the JSON in its existing layout, so a diff shows only the changed definitions.
11. **Where the result is recorded.** The device has no stored "verified" flag. Record a Test 1 pass through a named work, with its locator, in `seed/confidence-scoring.md`, and log a row in `app-decisions.md` stating the devices checked, the sources read, and each result (*agrees*, or the edit made and why). Say when a check could not be made.
12. **Finding devices that still need checking.** Start with the devices that fail Test 1, listed in `seed/confidence-scoring.md`; they are the ones nothing outside the AI vouches for. Then the `medium` and `low` devices, then the rest. Run the tests after any change.

## Review tag (agent only)
`device_review` (one row per device: `definition_reviewed`, `ai_example_reviewed`, `quote_changes`) is the agent's private review ledger, defined in `schema.sql`. Nothing in the app reads it: `items.py` and `server.py` select named columns, it is not in `seed/devices.json`, and `tests/test_add_device_review.py` fails if the app code mentions it. The agent reads it straight from `rhetoric.db`.

- `definition_reviewed`: set to 1 when the device's definition has been read against the Definitions rules above and the result recorded in `app-decisions.md`.
- `ai_example_reviewed`: set to 1 when the device's constructed example has been checked against the Constructed examples rules.
- `quote_changes`: how many times a credited quote has been written for the device. A trigger adds 1 for every insert of, or edit to, a credited example (a delete adds 0, a date edit adds 0), so 1 is the original quote and more than 1 means it was replaced or edited. A constructed example never counts.
- Set the two flags by hand in the same change as the review's `app-decisions.md` row; the counter needs no help. When a definition is edited after review, set the flag back to 0 until it is re-checked.
- A device row is created by trigger. `python3 -m seed.add_device_review` back-fills an older database and is safe to run twice. A rebuild from scratch discards the table, like the Topical tables, so back the database up first.
