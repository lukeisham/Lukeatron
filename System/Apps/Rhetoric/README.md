# Rhetoric

An offline, in-browser reference app for the rhetorical devices Luke draws on when preparing to teach. Each device has a definition, an AI-written example, a real quote, a popularity score and an AI-confidence rating, and *each group in the app is a different way in*. **Alphabetical** and **Popularity** are flat lists for *looking a device up* or seeing which are used most. **Category**, **Form** and **Function** show the three independent hierarchies the devices are *classified* by. **Topical** is *Luke's own arrangement*: Types he creates, nests and orders, with devices placed under them. **Grammar** files devices under *his own explained grammar labels*, which can also hold tables. **Index** lists *every real quote* by first line, source or date. **Compare** sets *a fallacy beside its Flipside*. **About** explains *how popularity and confidence are worked out*. **Topical** and **Grammar** are the *only* places the app lets him change anything; the rest is read-only. Search, the Display options, Copy and Print are *secondary*: they serve every group, for reading a chosen part on screen or taking it away as text or paper.

## Launch / restart
- Double-click `Start Rhetoric.command`, or run `python3 server.py` from this folder and open `http://127.0.0.1:8794`.
- To restart: close the Terminal window (or press Ctrl-C) and launch again. If it reports the port is in use, an earlier Rhetoric is still running.
- To rebuild the database from scratch, see `schema.sql` and the `seed/` modules (run from this folder with `python3 -m seed.<module>`). A rebuild discards Luke's Topical Types and placements and his Grammar labels and placements, so copy `rhetoric.db` first. `rhetoric.db` is tracked in git (it holds Luke's own labels and placements), so each commit is also a backup.
- To bring an older database up to the current schema without rebuilding it, run `sqlite3 rhetoric.db < schema.sql` (it only creates what is missing), then the matching `python3 -m seed.add_<name>` module: `add_example_attribution` (fills the tags from `seed/devices.json`), `add_quote_date`, `add_grammar_placements` (refuses while the old slot tables still hold rows), `add_label_tables`, `add_link_labels`, `add_topical_definition`, `add_topical_nesting` (keeps every Type as top-level) and `add_device_review`. Each is safe to run twice.

## Cross-app behaviour
**Display order.** Wherever a device is shown (list, Compare, Copy, Print), the order is device name, description, AI example, real quote. The order is fixed (see `app-decisions.md`). `app/render.js` draws the name, definition, Grammar explanation and examples in that order, and `items.py` (`_device_map`) sorts a device's examples so the AI example comes before its real quote whatever their row ids; `tests/test_items.py` covers it.

**Between apps.** Home launches Rhetoric: its `catalog.json` entry runs `server.py` from this folder's root on port 8794. Moving or renaming `server.py`, or changing the port, breaks that tile. The port is also fixed in `server.py` and `Start Rhetoric.command`. Rhetoric reads nothing from another app and no other app reads its data.

**Teaching App family.** Rhetoric is one of six apps (Rhetoric, Grammar, Logic, Research, Writing, Style) whose function (the code in `*.py`, `app/`, `seed/`, `tests/`, `schema.sql` and this README) is kept in step by `System/Tools/teaching-app-family/`: when a turn ends after code here changed, it offers the change to the others and carries it where Luke says. Data (the database, `images/`, `app-decisions.md`, `wishlist.md`, `app/about.html`) is never carried. Rhetoric's code has diverged, so it is only reported to, never merged.

**Between files.**
- `schema.sql` → `items.py`: table and column names; a rename breaks `/api/items` with a 500. `topical_rank` is not read by the app: Types and placements order the Topical view. `examples.attribution` is never null (`Unattributed` when none is recorded).
- `items.py` → `server.py` → `app/`: `GET /api/items` returns `trees` (one per hierarchy, device leaves as ids), a flat `devices` map with each device sent once, and a flat `quotes` list. Every sort, search and filter runs client-side on that payload. `server.py` checks the API route before serving `app/` as static files and returns 503 if the database cannot be opened (`app/api.js` treats any non-OK response as "could not load"). The database is opened read-only for `GET`; the only writes are the Topical and Grammar routes below, and any other POST, PUT, PATCH or DELETE gets 405.
- **Editing Topical and Grammar** share one write path. `server.py` (routing and the origin gate) → `topical.py` / `grammar.py` (the only SQL that writes) → `labeltree.py` (the move and depth rules both use) → `items.py` (rebuilds the tree to answer). Routes: `/api/topical/types` and `/api/grammar/labels` (`POST` to add), `/<id>` (`PUT` edit, `DELETE`), `/<id>/position` (`PUT`, `index` and an optional `parent_id`; 0 means top level), `/<id>/devices/<device id>` (`PUT` place, optionally at an `index`; `DELETE` remove) and `/<id>/tables` (`PUT`). Each answers `{topical: <tree>}` or `{grammar: <tree>}`, which `app/api.js` hands to `setEditableTree` in `state.js`, so the screen shows only what was saved. A write must carry this server's own `Host`, any `Origin` must match it and the body must be `application/json`, otherwise 403 or 400. Writes touch only the `topical_*` and `grammar_*` tables.
- Rules that two or more files must agree on: the depth limit of five (`MAX_DEPTH` in `topical.py` and `grammar.py`, `MAX_LABEL_DEPTH` in `state.js`; deeper is 400), `UNSORTED_ID` (0) in `topical.py` and `state.js`, names are free to repeat, even among siblings (the old sibling-name rule was removed 2026-10-07), a node with sub-nodes cannot be deleted (409), and a move under itself or past the depth limit is 400.
- **Tree shapes.** `trees.topical` and `trees.grammar` have the same shape as the other trees: each node lists its sub-nodes first, then its devices, and carries `tables`. Topical ends with a derived **Unsorted** node (id 0) holding every device with no Type; Grammar has no derived node and keeps every label even when empty. Node ids overlap between hierarchies, so an open heading is keyed `hierarchy:id` (`openKey` in `state.js`). Neither group is part of the no-group search.
- **Adding and filing devices.** `main.js` (`DEVICE_FORMS`, `fillDeviceTargets`, `onAddDeviceSubmit`, `fillParentPicker`) serves both groups' Add forms, with `app/picker.js` as the type-ahead; the forms are `#type-device-form` and `#grammar-bar` in `index.html`. A device may sit under any number of Types or labels.
- **Drag and drop.** `render.js` marks rows `draggable` and headings `data-droppable`; `drag.js` reports what was dropped where (with the group's `hierarchy`; a drop never crosses groups, and `zoneOf` sets where on a heading it landed); `main.js` (`movedTo`) turns that into a save, using `order.js` for the index, counted on the saved tree. The server decides whether a move fits (`labeltree.move`) and the group's status line shows a refusal. Dropping a device copies it; Unsorted cannot be moved or dropped onto.
- **Link labels.** A label or Type with `about_section` set (the id of its own section in `app/about.html`, `link-<name>`; NULL on every ordinary one) is a link: a leaf shown non-bold and underlined that goes to that section. The **Add link** button in each add form posts to `POST /api/grammar/links` or `/api/topical/links`; `labeltree.create_link` (shared by both) inserts the row and calls `aboutpage.add_section`, which appends the empty section and a contents line to the page, all in one transaction, so a page that cannot be written leaves no link. This is the only write outside the database, and a granted exception (`app-decisions.md`); `server.py` hands those two routes its `about_path` (`ABOUT_PATH`; tests pass a copy). `labeltree.require_plain` keeps a link empty: it refuses devices, tables, sub-labels and a move under it (400). The tree sends `about` on every node. On screen: `render.js` (`aboutLink`, `LINK_BUTTONS`), `drag.js` (`data-link`: dropped beside, never inside), `state.js` (`treeLabels` leaves links out of the pickers), `view.js` (Copy). Renaming or deleting a link leaves its About section, which Luke may have written in; section text is written by hand in `about.html`.
- **Label tables.** Stored in a `tables_json` column on `grammar_labels` and `topical_types`, written only through `grammar.set_tables` / `topical.set_tables`, which share `labeltables.py` for the shape (`{caption, colHeads, rowHeads, cells}`) and limits. `labeltables.py` and `app/tablegrid.js` must agree on those limits. `server.py` (`_as_tables`, body limit `MAX_TABLES_BODY_BYTES`) judges a body through `labeltables.clean`. On screen: `render.js` (`tableItem`), `app/tableeditor.js` and `tablegrid.js` (the editor), `main.js` (`editTable`), `view.js` (`tableToText` for Copy). `render.js` sets `--cols` and `--word` on each table, and `labeltable.css` fits the text with them and the tokens `--font-size-table-min` and `--table-char-width` in `tokens.css`.
- **Opening and closing headings.** `state.opened` and `toggleOpened`, `filterNode` in `view.js`; the choices made are kept in the browser under `rhetoric.opened` (`applyOpenChoices` in `state.js`, `loadOpenChoices` and `saveOpenChoices` in `settings.js`). A double click isolates one label or device through `isolateOrReturn` in `main.js`, and a single click waits `DOUBLE_CLICK_MS` so the two do not clash.
- `flipside_of` (a fallacy's id, or null) → `app/state.js` builds each device's shown `label` (`Fallacy/Flipside`). The list, Copy, search and flat sorts all read `label`, never `name`, so a new view must too. The device count (`#device-count`, `renderCount`) is the size of the loaded `devices` map.
- **Display options.** The field names in `state.js` (`showDefinitions`, `showAiExamples`, `showQuotes`, `showConfidence`, `showGroups`, `showLabels`, `showTypes`, `reveal`), the checkbox ids in `index.html`, the `hide-*` body classes in `list.css` and `TOGGLE_FIELDS` in `settings.js` must agree. Copy (`view.js`) honours the same options as the screen; `filingsOf` in `view.js` feeds the Category, Form, Function, Labels and Types lines in `render.js` and in Copy (`tests/test_filings.mjs`). Each example carries a kind (`example_kinds` in the payload, `exampleKinds` in state): `ai` for a constructed example, `quote` for a real one (`quotes.is_real_quote`); Show AI examples and Show quotes switch each kind separately, and `shownExamples` in `view.js` applies both to Copy. The AI-confidence badge is on screen only: `print.css` hides it and Copy omits it. Print and Copy carry only the list or table on screen. The About page has its own Print and Copy (`app/about.js`).
- `seed/` → `schema.sql`: the only writer. Stages hand files to each other in this order: `type_layers` (reads `seed/type-layers/*.md`) → `load_devices` (reads `seed/devices.json`, where each example is `{"text", "attribution"}` plus an optional `"date"`) → `popularity_pass` (the only network use; writes `seed/popularity.json`) → `update_popularity` (reads that file). `seed/db.py` applies the schema and holds the one writable connection. `topical_rank` is never set by the pipeline. `items.py` sends only the example text, so the screen does not show attributions.
- `ai_confidence_rating` crosses `seed/devices.json` → `load_devices.py` → `schema.sql` → `items.py` → `state.js` → `render.js` / `main.js` unchanged; `seed/guides/confidence-rubric.md` sets its meaning. Changing the allowed values (high|medium|low) breaks the schema CHECK, `RATING_TITLES` in `render.js` and the `data-rating` styles in `list.css` together.
- **About page.** `app/about.html` (styled by `about.css` on top of the shared masthead) is a static page linked from the toolbar. It restates in plain English the popularity method and the guides in `seed/guides/` (the rubric, definitions, constructed examples and quotes), so it changes with them and not with the data. Popularity comes from Google Books Ngram through the Skillbank skill `!DeviceMentions`, applied with `seed.update_popularity.apply_scores`; the mentions-to-score table assumes the top count in `seed/ngram_mentions.json`. Keep in step: the `SOURCES` list in `seed/popularity_pass.py` (`tests/test_about.py` fails if a source URL is not linked), the scale formula in `seed/classification-criteria.md`, and the rubric. Section numbers come from CSS counters in `about.css`, so text that points at a section ("§2") is updated by hand if sections move. The app version is typed by hand in the intro's `Version` line and has no other source.
- **Index group.** `quotes.py` decides what a real quote is and splits it into `text` and `source`; `seed/quote_status.py` reuses the same test. `items.py` sends them as `quotes` `{id, device_id, text, source, author, date}`; `state.js` maps them to `state.quotes`, `view.js` (`indexView`) builds the entries, `quoteindex.js` orders and groups them (`INDEX_ORDERS`), and `render.js` draws both forms, switched by the body class `index-full-on` in `index.css`. `indexFull` is in `TOGGLE_FIELDS`. `date` is the optional `quote_date` column of `examples`: `YYYY` or `YYYY-MM-DD`, a year under 1000 padded to four digits (AD 60 is `0060`), a year BC with a minus sign (935 BC is `-0935`, no year 0), NULL when unknown and never guessed. It is set as `"date"` on the example in `seed/devices.json` and written to a live database by `seed.add_quote_date`.
- **Compare group.** It opens from its own button (`#compare`), not from the group row: Compare is not in `SORTS`, but `OPENING_CHOICES` in `state.js` adds it for the "Open on" menu, whose options in `index.html` must match. `state.js` (`flipsidePairs`, `comparePairId`) builds the pairs from each Flipside's `flipsideOf`; `view.js` `compareView` returns `{mode: 'compare', pairs, current}`; `render.js` (`renderList`, `renderCompareBar`) draws the table and fills `#compare-bar`; `compareToText` in `view.js` serves Copy. Its three switches `tableNames`, `tableDefinitions` and `tableExamples` are separate from the Display menu: the checkbox ids `table-names|definitions|examples`, the `hide-table-*` classes in `compare.css`, `applyToggles` in `main.js` and `TOGGLE_FIELDS` in `settings.js` must agree. The cells show each device's own `name`, not its `label`.
- **Review ledger.** `device_review` is the agent's private table, defined in `schema.sql` and created by trigger; nothing in the app reads it (`items.py` and `server.py` select named columns, it is not in `seed/devices.json`, and `tests/test_add_device_review.py` fails if the app code mentions it). `python3 -m seed.add_device_review` back-fills an older database.
- Styling is split across `app/*.css` (`topical.css` the Topical editing controls and drag feedback, `compare.css` the Compare bar and table); `app/tokens.css` is the one file that defines a visual value. The list body is monochrome; the accent colour belongs to the masthead and toolbar zone only. `!HouseStyle` governs both.

**Guides for changing content.** Instructions an agent follows when it edits the seed data or the database, kept in `seed/guides/`:
- `change-workflow.md`: commit before and after any change.
- `quotes.md`: finding, checking and adding a real quote.
- `constructed-examples.md`: writing the AI example.
- `definitions.md`: writing and verifying a definition.
- `confidence-rubric.md`: setting `ai_confidence_rating` (the record of results is `seed/confidence-scoring.md`).
- `review-ledger.md`: keeping `device_review`.
