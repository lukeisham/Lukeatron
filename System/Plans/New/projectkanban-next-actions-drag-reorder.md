# Plan — ProjectKanban: drag-and-rearrange Next Actions, persisted to registry.md

## Objective
Let Luke drag a Next Actions row (in a project's detail view) to a new position and have that order persist back to the project's `registry.md`, through the same guarded write path (`writes.py`) every other per-row edit already uses — a real reorder of the file's Next Actions table, not a display-only convenience. This deliberately reverses `writes.py`'s own stated architecture decision — *"AD-2: named fields only, no positional API, which is also why there is no drag"* (line ~509; `writes.spec.md`'s own AD-2, now preserved only as this one code comment since the spec itself was deleted 2026-09-12 per the Phase 4 migration log) — with Luke's explicit go-ahead, given when this plan was scoped (2026-09-15, in preference to a client-side-only reorder). Specialises the Lukeatron North Star — *"extend it deliberately, never by accident"* — precisely by naming that reversal here, updating the comment that states it, and recording it in `refactor-registry.md`'s Migration log, rather than quietly coding around a decision the app's own source still asserts.

**Scope boundary (part of what "done" means here, not a later cleanup):**
- Reordering is supported only for a project whose Next Actions live in a **single** markdown table block (no stream sub-headings). A multi-stream project (rare — one fixture, `registry_multi_stream.md`, exists for this shape) renders with no drag affordance at all, plus a short note explaining why — `model.py` has no per-stream membership on its flat `tasks` list today, and inventing one is a separate, larger piece of work than this plan's.
- A linked row (🔗 Link stated) is never itself draggable or droppable-onto — it already has no edit controls (`buildLinkedRow`) and its canonical order lives wherever `!ProjectSweep` syncs it from. Other rows still reorder freely around it as a fixed anchor.
- Done rows (wishlist #4b's read-only list) are untouched — no reorder control there.

## Success criteria (measurable)
- `stores.py` gains a `multi_stream: bool` fact on the parsed registry record (reusing the same table-block-finding approach `writes._find_table_block_bounds` already mirrors), surfaced on `model.py`'s `ProjectView` as `multi_stream`, passed through with no derivation in `build_project`. `test_stores.py`/`test_model.py` prove it's `False` for every existing single-block fixture and `True` for `registry_multi_stream.md`.
- `writes.py` gains `reorder_next_actions(root, *, project_id, row_order, mtime) -> ReorderResult`: given the full ordered list of `#`/index values for every open, non-linked row in one table block, it locates the ONE block whose current row-id set exactly equals `set(row_order)` and rewrites only that block's data-row lines into the given sequence — every row's own cells carried through byte-identical, only line position changes. A `row_order` that doesn't exactly match any single block's row set raises a new `ReorderMismatchError` (covers a stale client, a multi-stream project, or a row that's since gone done/deleted) — nothing is written. Reuses the existing fence, mtime and re-parse-verify guards exactly as `set_cell` does; on success stamps `pending_sweep: true` and appends one `Logs/edits.log` line (`action=reorder_next_actions`), same as every other edit.
- `server.py`'s `/api/edit` gains a `"reorder"` field alongside the existing four cell fields and `note`: `_validate_edit_body` requires a `row_order` list of ≥2 unique non-empty string/int ids (never a bool); `ERROR_STATUS` gains `"reorder_mismatch": 422`; `_handle_edit` routes to `writes.reorder_next_actions` and catches `writes.ReorderMismatchError` alongside the existing `writes.*Error` cases.
- `edits.js`'s `ERROR_SENTENCES` gains a `reorder_mismatch` entry, worded for Luke (D-14/SR-9's standing rule), e.g. *"That list doesn't match what's on this row's table anymore — refresh and try again."*
- A new small module (e.g. `app/project/reorder.js`) owns the drag/drop wiring (native HTML5 drag-and-drop — no library, JS-7) and the reorder-then-submit flow; `task-row.js`'s solo/chip rows (not linked, not done) become `draggable="true"` with a small drag-handle affordance, reusing the row's existing `data-task-index`. `project.js` owns the network round-trip, mtime and error banner for the new `submitReorder`, exactly as it already does for `submitEdit` (task-row.js's own stated division of labour).
- **Keyboard parity, not drag-only:** each draggable row also gets "Move up"/"Move down" controls, each `aria-label`ed with the task's own action text (HTML-5), driving the identical reorder-then-submit path — native HTML5 drag-and-drop has no keyboard equivalent on its own, and every other control in this app already carries a real `aria-label` and a visible `:focus-visible` ring (task-row.css), so this is the bar the new controls are held to, not an optional extra.
- A drop (or a move-button press) reorders the rendered list immediately (optimistic), fires one `POST /api/edit` (`field: "reorder"`) with the new full order and the held `mtime`; a refusal reverts the list to its prior order and shows the existing error banner — mirroring exactly how `task-row.js`'s per-cell controls already revert on `{ ok: false }`.
- A `multi_stream: true` project renders every row with no drag handle and no move buttons, plus one short explanatory note near the "Next Actions" heading (JS-2 — no silent absence).
- Test coverage: `test_writes.py` (happy path — order verified on disk, cells untouched; `ReorderMismatchError` on a non-matching row set, nothing written; `StaleMtimeError` still refuses before any file touch — TEST-7's blocked/permitted pair); `test_server.py` (the `reorder` field's validation and happy path); `test_stores.py`/`test_model.py` (`multi_stream` as above); `tests/test_project.mjs` or a new `test_reorder.mjs` (drag handles/move buttons present or absent + note per `multi_stream`; a simulated drop calls the injected edit client with the expected `{field: "reorder", row_order}` payload and reverts on refusal; the move-up/move-down buttons produce the identical payload as an equivalent drag).
- Full suite green: every `node tests/test_*.mjs` and `python3 -m unittest discover` from `_template/` exit 0 — the two pre-existing, already-logged failures aside.
- Verified live on `:8789` against a real single-block project: a drag reorders the on-screen list, survives a re-fetch/reload, and the underlying `registry.md`'s Next Actions table shows the new order with every other cell unchanged; the move-up/move-down buttons produce the same on-disk result; a multi-stream project shows no drag affordance plus the note; the whole interaction (handle and buttons) is reachable and operable by keyboard alone with a visible focus ring throughout.
- `writes.py`'s own header comment and its "AD-2 ... which is also why there is no drag" line are updated to describe the new capability instead of contradicting it.
- `System/Apps/ProjectKanban/refactor-registry.md` gets one new dated Migration log row naming this as a deliberate reversal of the prior no-drag decision, with Luke's go-ahead recorded; `wishlist.md` gets a new row marked `built`.
