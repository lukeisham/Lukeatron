# Ideas

One of the applications built on **MarkAs** conventions (files, folders,
and naming, per "convention over configuration") as part of **Synergy**.
Manages everything in a product's `Ideation/` space: turning raw, messy
notes into a problem statement, a few candidate solutions, and a
deduplicated set of fleshed-out feature ideas (product requirements) — the
pre-spec phase that precedes the `specs` skill.

## Files this skill owns

```
Ideation/
  <product>.problem.md              the problem being solved, and who has it
  <product>.solution.md             symlink -> Solutions/<chosen>.solution.md
  <product>.<kind>.description.md   comprehensive informal narrative — generated by /ideas-describe; frontmatter: phase (only if Features/ is phase-divided)
  <product>.dependencies.md         other products this one depends on — generated by /ideas-solution
  PHASES.md                         phase order and which phase is active — see "Phasing" below, generated/updated by /ideas-phase
  Ideas/
    <whatever the human drops in>     raw, unprocessed idea notes — the inbox, pre-triage
    Phase1/, Phase2/, ...             optional — present only once /ideas-phase has divided this folder
  Solutions/
    <proposed-solution>.solution.md   one file per candidate solution
  Features/
    <feature-name>.feature.idea.md    one file per feature idea — frontmatter: inclusion, status (see below)
    Phase1/, Phase2/, ...              optional — same as Ideas/ above
  Issues/
    <slug>.issue.md                 one file per integrity issue — frontmatter: status (see below); never deleted, marked resolved in place
    Phase1/, Phase2/, ...              optional — same as Ideas/ above
```

`<product>` matches the root `<Product>.product.spec.md` if one exists,
else the repo's folder name. Nothing written here is a full spec — once a
feature idea is mature, it graduates to the `specs` skill.

`Ideas/` is where new raw material belongs going forward — drop new
notes, brain dumps, or externally-authored idea files there rather than
loose at the `Ideation/` root. (Older repos may still have raw material
sitting loose at the root from before this folder existed — that's fine,
still treat it as a raw note per step 1, no need to migrate it
retroactively unless asked.)

`Ideas/`, `Solutions/`, `Features/`, and `Issues/` are created on first
use if they don't already exist. `/ideas-init` creates all four
explicitly and idempotently; `/synergy-init` also ensures they exist as
part of scaffolding a repo's spaces. Never scaffold empty
`.problem.md`, `.solution.md`, or per-item files — those come from real
notes, not initialization.

## Feature idea frontmatter (`inclusion`, `status`)

Every `Features/<name>.feature.idea.md` carries YAML frontmatter with two
independent decision fields:

```yaml
inclusion: proposed
status: pending
```

- **`inclusion`** — the product decision on whether this feature gets
  built: `proposed` (default, not yet decided), `selected` (in scope),
  `deferred` (worth doing, just not now), `dropped` (not doing it).
- **`status`** — the review state of the write-up itself: `pending`
  (default, not yet reviewed), `approved` (the human has confirmed it's
  accurate and ready), `rejected` (reviewed, and it needs rework or
  doesn't hold up). `/ideas-mine` calls these states "draft" and
  "complete" — same field, same values, just the vocabulary that command
  uses while it works one idea at a time.

New feature ideas are always written with both at their defaults
(`proposed` / `pending`) — never pre-decided on the human's behalf.
Whoever writes or re-reads a feature idea (step 6 below, `/ideas-feature`,
`/ideas-fix`, ingesting new notes) checks the current values first and
**only asks the human about a field that's still at its default** —
`inclusion` only if it's still `proposed`, `status` only if it's still
`pending`, and each independently (a feature can be `selected` while
still `pending` review, or vice versa). Once the human sets a field to
something else, it's a recorded decision, not a standing question to
re-ask on every later pass. `/ideas-check` is the one exception to
"asks" — being read-only, it only *lists* which features are still
undecided, it never interviews the human about them itself.

A feature idea's **phase**, if this Ideation space is phased at all, is
not a frontmatter field — it's which `Features/Phase<N>/` subfolder the
file physically lives in (or no subfolder, if `Features/` hasn't been
divided, or if the feature hasn't been triaged into a phase yet). See
"Phasing an overwhelmed Ideation space" below.

## Issue frontmatter (`status`)

Every `Issues/<slug>.issue.md` carries YAML frontmatter with one field:

```yaml
status: outstanding
```

- **`status`** — `outstanding` (default, not yet resolved) or `resolved`.
  The machine-checkable twin of the body's own `## Resolution` section
  (see "Issues and integrity" below): the frontmatter is what tools
  check, the body is what a human reads for the story and the date.

Like feature ideas, an issue's **phase** is not a frontmatter field —
it's which `Issues/Phase<N>/` subfolder the file physically lives in (or
no subfolder, if `Issues/` hasn't been divided, or the issue hasn't been
triaged into a phase yet). Keeping phase purely structural — the same
mechanism as `Ideas/` and `Features/` — avoids two places (a frontmatter
field and a folder) that could silently drift out of sync; see "Phasing
an overwhelmed Ideation space" below.

Every issue gets its `status: outstanding` frontmatter the moment it's
filed, whether by `/ideas-fix` or inline while ingesting new notes (see
"Ingesting new idea notes dropped in later" below). `/ideas-check`
reports any issue file missing this frontmatter; `/ideas-fix` adds it
automatically (a safe, unambiguous auto-fix, the same tier as a missing
feature-idea frontmatter block) rather than leaving it unmarked.

## Commands in this skill

Beyond the interactive workflow below, this skill has grown dedicated
commands for its more self-contained steps. Typical order on a live
project: drop notes in `Ideas/` and run the workflow, or pitch the
problem directly with `/ideas-problem` → `/ideas-solution` to add or
choose a solution → `/ideas-feature` once a solution is selected →
`/ideas-describe` once features exist → `/ideas-check` any time integrity
is in doubt, `/ideas-fix` to act on what it finds. `/ideas-init` is no
longer a required first step —
`/ideas-problem` and `/ideas-solution` both scaffold the four structural
folders themselves before doing anything else, since either may be the
very first command run in a fresh Ideation space — but it's still there
for scaffolding explicitly ahead of time (e.g. from `/synergy-init` or
`/utopia-init`).

- **`/ideas-problem <pitch>`** — draft or refine the problem statement
  from a pitch, then propose candidate solutions against it. See
  "Drafting a problem" below.
- **`/ideas-solution <pitch>`** — draft or merge a candidate solution
  from a one-line pitch, prompt a solution choice, then identify the
  chosen solution's dependencies. See "Capturing a solution pitch" below.
- **`/ideas-feature`** — cluster raw ideas into `Features/*.feature.idea.md`,
  issue-aware per "Issue-awareness beyond `/ideas-check`/`/ideas-fix`"
  below. See "Generating feature ideas" below.
- **`/ideas-mine [hint]`** — extract one idea at a time from messy raw
  notes into a single, carefully drafted and gap-filled feature idea,
  instead of `/ideas-feature`'s bulk pass over everything; also
  issue-aware. See "Mining one idea at a time" below.
- **`/ideas-describe`** — narrate the product into
  `<product>.<kind>.description.md`, issue-aware. See "Narrating a
  description" below.
- **`/ideas-check`** — read-only: reports integrity problems (including
  missing issue-status frontmatter) and a pipeline-progress
  recommendation, changes nothing itself; see "Issues and integrity"
  below.
- **`/ideas-fix`** — the mutating counterpart to `/ideas-check`:
  auto-fixes what's safe (including adding missing issue-status
  frontmatter), files issues for what isn't, asks the human to resolve
  open issues and undecided features, then applies the answers; see
  "Issues and integrity" below.
- **`/ideas-init`** — idempotently scaffold `Ideas/`, `Solutions/`,
  `Features/`, `Issues/` ahead of time; optional given the above.
- **`/ideas-phase`** — interview the human to divide `Ideas/`,
  `Features/`, and/or `Issues/` into `Phase1/`, `Phase2/`, ... subfolders
  when the space has gotten too large or contradictory to work through
  at once; see "Phasing an overwhelmed Ideation space" below. Reached
  for as needed, not part of the linear order above.

## Drafting a problem (`/ideas-problem`)

`/ideas-problem <pitch>` starts by idempotently scaffolding `Ideas/`,
`Solutions/`, `Features/`, and `Issues/` (same as `/ideas-init`) — it may
be the first command run in a fresh Ideation space, and everything after
assumes those folders exist. Then it takes the user's own description of
the problem as command arguments, interviews them on whatever it leaves
underspecified (who has the problem, why it matters now, non-goals), and
delegates to a **Fable**-backed subagent (`Agent` tool, `model:
"fable"`, `subagent_type: "Plan"`, foreground) to write `<product>.problem.md`
— merging into an existing one if it's already there, rather than
overwriting a first draft blindly — and to propose 2–4 genuinely distinct
candidate solutions against it, written to `Solutions/*.solution.md`.
This operationalizes the skill's own steps 2 and 3 as a single
self-contained command. It ends by presenting the candidates for review
and pointing at `/ideas-solution` as the next step, to pitch a solution
of its own, refine a candidate, or choose one outright.

## Capturing a solution pitch (`/ideas-solution`)

`/ideas-solution <pitch>` also starts by idempotently scaffolding the
same four folders, for the same reason — it too may be the first command
run in a fresh space. Then it takes the user's own one-line (or longer)
description of a suggested solution as command arguments, checks it
against every existing `Solutions/*.solution.md`, and either merges it
into an existing candidate that already covers the same approach or
writes it as a new one — never a near-duplicate second file for the same
idea. The merge-or-new judgment and the initial write-up are delegated to
a **Fable**-backed subagent (`Agent` tool, `model: "fable"`,
`subagent_type: "Plan"`, foreground), then fleshed out by interviewing
the user on whatever the pitch left underspecified. It presents every
current candidate side by side and asks the user to choose one
explicitly, per this skill's own step 7 — symlinking `<product>.solution.md`
immediately once they do, per step 8.

Once a solution is chosen, `/ideas-solution` also identifies that
solution's **dependencies on other products** — a sister product, or a
lower layer in the module hierarchy this one builds on — into
`Ideation/<product>.dependencies.md`. It asks the user directly whether
the solution depends on anything, and for any dependency that's a "hole"
(implied but not yet named), asks what fills it: a custom sister product
or a third-party one, either way with a concrete name. Once named, each
dependency is researched — checking sibling product folders in this
repo's parent workspace first (per the `meta` skill's model), falling
back to a web search for anything not found locally — and the reference
found (or "not yet built," for a planned sister product) is recorded
alongside it. No dependencies means no file — this step never scaffolds
an empty one. It closes by recommending `/specs-depend` (not built yet —
named as a future step, never invoked) to pull in a product brief for
each listed dependency.

## Generating feature ideas (`/ideas-feature`)

`/ideas-feature` reads the raw notes in `Ideas/` (walking into
`Phase<N>/` subfolders if `Ideas/` has been divided, per "Phasing" below
— but always including whatever sits at `Ideas/`'s own top level too,
since that's where cross-phase or not-yet-triaged raw material lives),
the problem statement, the *selected* solution (`<product>.solution.md`,
not the other candidates), any existing `<product>.<kind>.description.md`,
and any relevant images under `Ideation/`, then clusters them into
aggregated, informal `Features/<name>.feature.idea.md` write-ups — one
per feature, merging notes that describe the same feature rather than
producing one file per note. Each feature references the source notes it
aggregates and is a preparatory step before formal feature specs (a
`_Builds/` mini-PRD, or a top-level PRD's requirements via
`/specs-prd`), not a spec itself. Requires a resolved
`<product>.solution.md` — features are built against the *chosen*
solution, not candidates still under consideration; `/ideas-solution`
gets one chosen if none is yet. Clustering and drafting are delegated to
a **Fable**-backed subagent (`Agent` tool, `model: "fable"`,
`subagent_type: "Plan"`, foreground); it fills obvious gaps itself and
flags only what it can't determine easily for the user to resolve
directly. New feature files land in `Features/Phase<active>/` if
`Features/` has been divided (per "Phasing" below), else directly in
`Features/`. Safe to re-run as new notes accumulate — existing feature
files are updated in place, wherever they currently live, per the
"ingesting new notes" discipline below, not duplicated. New features get
`inclusion: proposed` / `status: pending` frontmatter; before review, the
user is asked to decide both for every feature still at either default —
new or pre-existing — per "Feature idea frontmatter" above. Also reads
`Issues/*.issue.md` per "Issue-awareness beyond `/ideas-check`/
`/ideas-fix`" below before drafting. The draft is reviewed with the user
before anything is committed, same as `/ideas-describe`; ends by
prompting the user to run `/ideas-describe` next.

## Mining one idea at a time (`/ideas-mine`)

`/ideas-mine [hint]` is the focused counterpart to `/ideas-feature`'s
bulk clustering pass: instead of turning *all* the raw notes into
features in one go, it works **one idea at a time**, with a real
back-and-forth, for the case where a pile of messy notes has one idea in
it worth careful attention (or where a bulk pass already left something
under-developed). `[hint]`, given as command arguments, narrows which
idea to mine — a keyword or short description, not a command to act on
directly.

If the hint is missing or ambiguous (matches more than one distinct
topic in the raw notes), it identifies a short list of candidate
ideas — the same clustering judgment `/ideas-feature` uses, delegated to
a **Fable**-backed subagent — and asks the user which to work on first,
rather than guessing. If `Ideas/` has been divided into `Phase<N>/`
subfolders (per "Phasing" below), candidates come from the active
phase's subfolder (plus whatever sits at `Ideas/`'s own top level, since
that's cross-phase or untriaged material) by default; mining something
from a deferred phase's subfolder needs explicit confirmation, since it
was set aside on purpose.

Once a candidate is settled, the process is genuinely iterative, not a
single draft-and-done: a Fable-backed subagent extracts a first draft
into `Features/<name>.feature.idea.md` (merging into an existing feature
if one already covers the same idea, same discipline as `/ideas-solution`'s
merge-or-new judgment; a new file lands in `Features/Phase<active>/` if
`Features/` has been divided, else directly in `Features/`) — this is
the **draft** state, `status: pending`. The user reviews it, then is
asked for anything more to add. Only after that does the command
analyze the write-up for gaps and interview the user to fill them — a
real gap-finding pass, not a rubber stamp on the first draft. Once gaps
are resolved and the write-up holds up, `status` moves to `approved` —
this command's **complete** state (same field as everywhere else, see
"Feature idea frontmatter" above). If gaps remain because the user
couldn't answer or explicitly deferred them, the file stays `pending`
and the open gaps are recorded in it directly, not dropped. `/ideas-mine`
never touches `inclusion` — drafting a solid write-up and deciding
whether to build it are separate questions, left to
`/ideas-check`/`/ideas-fix`. Also reads `Issues/*.issue.md` per
"Issue-awareness beyond `/ideas-check`/`/ideas-fix`" below — an
outstanding, in-phase issue about the idea being mined is worth
resolving as part of the same pass, not a separate concern.

## Narrating a description (`/ideas-describe`)

`/ideas-describe` reads every **eligible** `Features/*.feature.idea.md`
— and only those, since feature ideas already aggregate the raw notes,
the problem, and the selected solution per `/ideas-feature` — and
narrates them into one comprehensive, informal description:
`Ideation/<product>.<kind>.description.md`. Unlike everything else this
skill or `specs` produces, it's deliberately prose, not a typed/numbered
document — the readable overview you'd hand someone to explain what the
thing *is*. `<kind>` names what's being described (`product`, `language`,
`utility`, ...) and becomes part of the filename, so it's confirmed with
the user rather than guessed when unclear.

A feature is **eligible** only with `inclusion: selected`,
`status: approved` (`/ideas-mine`'s "complete," not "draft"), and — if
`Features/` has been divided into `Phase<N>/` subfolders (per "Phasing"
below) — physically located in the active phase's subfolder or an
earlier one; a feature still sitting at `Features/`'s own top level
(not yet triaged into any phase) is treated as untriaged and excluded,
not guessed into either bucket. The point: the product description
should reflect what's actually decided-to-build and finished, in the
part of the space currently being worked, not every half-considered
proposal or something deliberately deferred to a later phase. It
requires at least one *eligible* feature idea to exist — if none do
(because none exist yet, or none yet clear the bar), it says which,
pointing at `/ideas-feature`/`/ideas-mine`, `/ideas-check`/`/ideas-fix`,
or `/ideas-phase` as appropriate rather than a generic "nothing here."
Before narrating, it also reads `Issues/*.issue.md` per "Issue-awareness
beyond `/ideas-check`/`/ideas-fix`" below — a description shouldn't
narrate around a contradiction its own drafting happens to resolve
without saying so.

If `Features/` is phase-divided, the written file is stamped with
`phase: <N>` frontmatter, `<N>` being the active phase used for
eligibility above — the description always records *which phase's*
feature set it reflects, rather than reading as a complete, final
picture when it's actually scoped to what's active right now. If
`Features/` isn't phase-divided, no frontmatter is added — there's
nothing to record. Re-running `/ideas-describe` later updates this
frontmatter to match whatever phase is active at that point.

The draft is reviewed with the user before anything is committed; this
command only *offers* to commit and push after that review, never
automatically, even inside a Utopia repo.

## Workflow

Before step 1, ensure the four structural folders exist: idempotently
create `Ideas/`, `Solutions/`, `Features/`, and `Issues/` (same as
`/ideas-init`) if any are missing, leaving any that already exist
untouched. Do this regardless of entry point — this interactive workflow,
`/ideas-problem`, or `/ideas-solution` — before reading notes, drafting
the problem, proposing solutions, or asking the human to choose one.

1. **Read every raw note in the Ideation space.** Raw notes live in
   `Ideas/` going forward (older repos may still have some loose at the
   `Ideation/` root — read those too). A raw note is anything that
   doesn't match this skill's own naming conventions — brain dumps,
   half-formed text, pasted transcripts. Read all of them before
   synthesizing; a missed note means a missed feature or a wrong problem
   framing.

2. **Draft the problem statement.** Delegate to a **Fable**-backed Plan
   agent (see Model policy) — resolving what the real problem is from messy
   notes is the highest-ambiguity step here. Hand it the raw text and ask
   for: the problem, who has it, why it matters now, and any non-goals it
   can infer. Write `<product>.problem.md`. If notes conflict on what the
   problem even is, surface the conflict to the human rather than silently
   picking one.

3. **Propose a few candidate solutions.** Same Fable Plan agent (continued,
   or fresh with the problem statement plus raw notes as input). Produce
   2–4 genuinely distinct candidates, not variations on one idea. Write
   each as `Solutions/<name>.solution.md` — approach, key tradeoffs, and
   why it would or wouldn't work given the problem statement.

4. **Interview the human to clarify.** Before going further, surface open
   questions the notes don't answer: ambiguous scope, conflicting
   priorities, unstated constraints. Ask directly rather than guessing —
   this is the cheapest point to correct direction, before feature work is
   invested.

5. **Organize ideas into features.** Cluster the raw notes and solution
   detail into candidate features — a flat list, short name plus one-liner
   each, deduplicated. Where two notes describe the same feature
   differently, merge them; where they contradict, flag it for the human.

6. **Flesh out each feature idea.** For every feature the human confirms is
   worth pursuing, write `Features/<feature-name>.feature.idea.md`: what it
   is, why it matters to the problem/solution, and roughly what it would
   take. Enough for someone to decide whether to build it — not a full spec.
   Write it with `inclusion: proposed` / `status: pending` frontmatter
   (see "Feature idea frontmatter" above), then ask the human right away
   to decide both — don't leave a freshly written feature sitting at its
   defaults as an unasked question.

7. **Ask the human to choose a solution.** Present the candidates in
   `Solutions/` side by side, with the tradeoffs from step 3, and get an
   explicit choice. Don't pick for them.

8. **The moment the human chooses, symlink it — don't defer this.**
   Creating `<product>.solution.md` is not a separate cleanup step; it is
   part of *answering* step 7. As soon as the human names a choice, before
   doing anything else with that answer, from the **repo root** (don't
   `cd` into `Ideation/` first — see the caution below):
   ```
   ln -sf "Solutions/<name>.solution.md" "Ideation/<product>.solution.md"
   ```
   If `<product>.solution.md` already points at a different solution,
   confirm with the human before repointing it — that's a direction
   change, not routine maintenance. If it's dangling (points at a solution
   file that no longer exists) or missing outright while exactly one
   solution file exists, treat that as a bug to fix immediately, not
   something to wait on `/ideas-check` for.

   **Caution — get this path split right or the symlink silently breaks:**
   only the *second* argument (the symlink's own location) gets the
   `Ideation/` prefix; the *first* argument (what it points at) never
   does. A symlink's relative target is resolved against the symlink's
   *own* directory when read, not against whatever directory the `ln`
   command happened to run from — so `Solutions/<name>.solution.md` is
   already correct once the link itself lives inside `Ideation/`.
   Prefixing the first argument too (`Ideation/Solutions/...`) or running
   the command exactly as shown but from inside `Ideation/` while still
   using an unprefixed second argument are the two ways this goes wrong:
   both create a symlink that `ln` reports success for but that fails to
   resolve on read. After creating or repointing it, verify with `cat
   Ideation/<product>.solution.md` (not just `ls`, which won't show a
   dangling link) before treating step 7 as answered.

## Ingesting new idea notes dropped in later

Raw notes don't stop after the first pass — the human may drop new notes,
externally-authored idea files, or pasted material into `Ideas/` at any
time (matching step 1's definition: anything that doesn't match this
skill's own naming conventions). New material always lands at `Ideas/`'s
own top level, even if `Ideas/` has already been divided into
`Phase<N>/` subfolders — it hasn't been triaged into a phase yet, so it
doesn't belong in one. When this happens:

1. Read the new material in full, alongside the existing
   `<product>.problem.md`, `<product>.solution.md`, and every
   `Features/<feature-name>.feature.idea.md` (wherever it lives, phased
   or not).
2. For each thing the new material says that bears on an existing feature
   idea: if it's additive or clarifying, update that feature idea file
   directly and say what changed — leave its `inclusion`/`status`
   frontmatter as the human last set it; new notes inform the write-up,
   they don't silently reopen a decision. If it contradicts an existing
   feature idea, the problem statement, or the chosen solution (including
   material that undercuts a feature already `selected` or `dropped`), do
   **not** silently overwrite — file an issue instead (see below) and
   leave the existing file, and its frontmatter, as-is until the human
   resolves it.
3. For anything that describes a genuinely new feature, flesh it out as a
   new `Features/<feature-name>.feature.idea.md` per step 6, including
   asking the human to decide its `inclusion`/`status`.
4. Report what was updated, what was added, and what was filed as an
   issue.

## Issues and integrity (`Issues/`, `.issue.md`, `/ideas-check`, `/ideas-fix`)

`Issues/<slug>.issue.md` records anything this skill finds that it can't
safely resolve on its own: a contradiction between two feature ideas, a
new note that conflicts with the problem statement or chosen solution, a
dangling reference (e.g. `<product>.solution.md` pointing at a solution
file that no longer exists), a duplicate or near-duplicate feature. Each
issue file carries `status` frontmatter (see "Issue frontmatter" above)
and states what's inconsistent and the files involved; once answered,
it's amended with the human's resolution and what changed as a result.
**Issues are never deleted** — mark a resolved issue by setting `status:
resolved` in its frontmatter and appending a `## Resolution` section
(with a `Resolved: <date>` line plus the resolution itself) to the body,
and leave it in place as an audit trail of decisions made. Two things
write these: step 2 of "Ingesting new idea notes dropped in later"
(inline, while already mutating something else) and `/ideas-fix` (a
dedicated pass over everything at once). A newly filed issue lands
wherever its subject matter's phase already lives structurally — e.g. an
issue about a `Features/Phase2/` feature goes in `Issues/Phase2/` if
`Issues/` has been divided that way, or at `Issues/`'s own top level if
it hasn't been divided, or if the issue doesn't cleanly belong to one
phase (see "Phasing" below).

**`/ideas-check` and `/ideas-fix` are a read/write pair** covering the
same ground — checking vs. acting — so nothing has to be duplicated
between them; read whichever one you need.

The `/ideas-check` command is **read-only** — checking, warning, and
recommending, nothing else. It never writes, edits, or deletes a file,
and never runs `/ideas-problem`, `/ideas-solution`, `/ideas-feature`, or
`/ideas-describe` itself. It scans `Ideation/` to determine which
pipeline steps are done — problem (`<product>.problem.md` exists),
solution (`<product>.solution.md` exists and resolves), feature (at
least one `Features/*.feature.idea.md` exists, at top level or in any
`Phase<N>/` subfolder), describe (`<product>.<kind>.description.md`
exists) — and *names* the earliest undone step's command in its report,
without running it. It then *detects and reports*, without fixing or
filing: dangling symlinks, orphaned files, naming-convention violations,
untriaged raw notes, contradictions between feature ideas or against the
problem/solution (judgment work delegated to a Fable-backed subagent for
detection only, same as elsewhere in this skill), every
`Features/*.feature.idea.md` still at `inclusion: proposed` or `status:
pending` (wherever it lives), every `Issues/*.issue.md` missing its
`status` frontmatter, and every issue whose frontmatter `status` is
`outstanding`. Both the undecided-features and open-issues checks are
scoped to the active phase, independently per folder, when that folder
has been divided into `Phase<N>/` subfolders (per "Phasing" below): items
in the active phase's subfolder (or at the folder's own top level, for
untriaged/cross-phase material) are individually listed; items in a
later, not-yet-active phase's subfolder are just counted, not itemized.
A folder with no `Phase<N>/` subfolders at all is treated exactly as
before phasing existed — everything in it is in scope, nothing excluded.
None of this is persisted by `/ideas-check` itself — a contradiction it
spots doesn't become a new `Issues/` file unless the human acts on the
report, typically by running `/ideas-fix`. Safe to run as often as you
like precisely because it can't change anything.

The `/ideas-fix` command is the mutating counterpart, doing the same
inventory and detection as `/ideas-check` but acting on it: it fixes
what it safely can on its own (dangling symlinks with an unambiguous
target, orphaned files, naming-convention violations, and any
`Issues/*.issue.md` missing its `status` frontmatter — inferring it from
whether the body already has a `## Resolution` section), writes
`Issues/<slug>.issue.md` for anything it can't safely resolve, asks the
human to resolve each outstanding, in-phase issue *and* every
`Features/*.feature.idea.md` still at its default `inclusion`/`status`
(same active-phase-per-folder scoping as `/ideas-check`), then applies
the fixes those answers imply and marks the corresponding issues resolved
(`status: resolved` in frontmatter, `## Resolution` appended to the
body). Like `/ideas-check`, it never runs `/ideas-problem`,
`/ideas-solution`, `/ideas-feature`, or `/ideas-describe` itself — its
report only names the recommended next pipeline command. Run it any time
after dropping in new notes, or whenever `/ideas-check` (or your own
judgment) says the Ideation space's consistency or pipeline progress is
in doubt.

The `/ideas-init` command ensures the four structural folders
(`Ideas/`, `Solutions/`, `Features/`, `Issues/`) exist — idempotent,
creates only what's missing. Run it once when adopting this skill in a
repo that doesn't have them yet; `/synergy-init` also covers this as part
of scaffolding a repo's spaces, so you rarely need to run both.

### Issue-awareness beyond `/ideas-check`/`/ideas-fix`

`/ideas-feature`, `/ideas-describe`, and `/ideas-mine` all read
`Issues/*.issue.md` and their `status` frontmatter (plus, when `Issues/`
is phase-divided, which `Phase<N>/` subfolder each one is in) before
doing their own work, per two rules:

- **Ignore out-of-phase issues.** An issue physically sitting in a
  `Phase<N>/` subfolder later than the active phase isn't this run's
  concern — don't let it block, influence, or get re-litigated by work
  happening in an earlier phase. If `Issues/` hasn't been divided, there's
  no "later phase" to ignore, so this doesn't exclude anything.
- **Attempt to resolve outstanding, in-phase issues where appropriate.**
  If the work the command is already doing — clustering features,
  narrating a description, mining one idea — naturally touches what an
  `outstanding`, in-phase (or undivided-folder) issue is about, and the
  command's own output actually resolves the inconsistency the issue
  names, resolve it inline: set `status: resolved` in the issue's
  frontmatter and append a `## Resolution` section, the same mechanic
  `/ideas-fix` uses and that "Ingesting new idea notes dropped in later"
  already does for contradictions found while updating a feature. This is
  opportunistic, not a mandate — don't expand scope to go hunt down an
  issue unrelated to the task at hand. Anything the command's own work
  doesn't naturally resolve stays open for `/ideas-check`/`/ideas-fix` to
  handle deliberately.

Each command's own section above notes where this applies; this is the
shared rule they all point back to.

## Phasing an overwhelmed Ideation space (`Phase<N>/`, `PHASES.md`, `/ideas-phase`)

An Ideation space can outgrow being worked through in one pass: a big
initial note-dump produces more raw material and candidate features than
anyone can sensibly decide on at once, and the signs show up as exactly
the things `/ideas-check` already detects — a pile of open issues, a
long tail of contradictions, and (the clearest tell) `Features/*.feature.idea.md`
that stay `inclusion: proposed` across more than one `/ideas-check` or
`/ideas-fix` run because there are simply too many to decide on together.
**Phasing** is the fix: split everything into an ordered set of phases,
work phase 1 to resolution, and defer the rest without losing track of
it.

**Recognizing when to suggest it** is a judgment call, not a fixed
threshold, but the signal is the combination of *volume* and *stuck
decisions* — roughly, more open issues plus still-`proposed` features
than would fit in a couple of `AskUserQuestion` batches (a handful is
fine, well into double digits usually isn't), especially if the same
ones are still undecided after a prior `/ideas-check` or `/ideas-fix`
pass already surfaced them. Any part of this skill can notice this and
propose phasing — the core workflow while clustering features (step 5),
`/ideas-feature` while drafting them, and `/ideas-check`/`/ideas-fix`
explicitly recommend it in their report when the signal is there and no
folder has been phase-divided yet. Recommend, don't impose: propose the
idea, explain why (the specific pile that prompted it), and let the human
decide whether to act on it now.

**Phase membership is physical, not a manifest.** Once a folder is
divided, an item's phase is simply which `Phase<N>/` subfolder it lives
in directly under `Ideas/`, `Features/`, or `Issues/` — there is no
separate list to keep in sync (deliberately unlike the feature-idea
`inclusion`/`status` frontmatter, which *is* the record for those
decisions). An item still sitting at its folder's own top level, once
that folder has been divided, is untriaged — not yet assigned to a
phase — and is treated the same way whether that's because it's new and
hasn't been sorted yet, or because (for `Ideas/` specifically, see
below) it genuinely doesn't belong to just one phase.

**Division is per-folder, and partial.** `Ideas/`, `Features/`, and
`Issues/` are divided independently — a space might phase `Features/`
first and leave `Issues/` undivided for a while, or vice versa. A folder
with no `Phase<N>/` subfolders is simply not phased yet: every command
treats it exactly as it would if phasing didn't exist at all, no
exclusions. This is "some but not all Ideation folders may be divided by
phases," and every command that reads phase state must check per-folder,
not assume that if one is divided they all are.

**The `Ideas/` exception — raw material that spans phases stays put.**
Raw notes are messier than features or issues: a single note, or a raw
notes subfolder (e.g. one Ulysses export group), often touches more than
one phase's worth of material, or hasn't been cleanly triaged at all.
When dividing `Ideas/` (or moving new raw material into a phase later),
**a note or raw-notes subfolder only moves into `Ideas/Phase<N>/` if it
belongs cleanly to that one phase.** Anything that spans phases, or is
too tangled to confidently assign, **stays at `Ideas/`'s own top
level** — never forced into a subfolder it doesn't cleanly belong in.
This exception is specific to `Ideas/`; `Features/*.feature.idea.md` and
`Issues/*.issue.md` are each about one thing already, so they don't
usually have this problem — if one genuinely does span two phases,
treat it as untriaged (top level) rather than picking arbitrarily.

**When the human agrees to phase a folder**, the flow (via `/ideas-phase`,
or reached proactively) is: present the full unphased pool in that
folder — everything currently at its top level — and ask which belong in
**phase 1**, the one to work now. **Everything not explicitly placed in
phase 1 defaults to phase 2** — a single deferred catch-all, not a
demand to sort every item individually; the human only has to name
what's urgent. A Fable-backed subagent may propose a starting phase-1
grouping (e.g. foundational items, or the least contradictory subset) to
react to rather than sort from scratch, but the human's placement is
final. Once decided, `/ideas-phase` physically moves each item with
`git mv` (falling back to `mv` outside a git repo) into
`<Folder>/Phase1/` or `<Folder>/Phase2/`, creating those subfolders if
they don't exist yet — applying the `Ideas/` exception above when that's
the folder being divided.

**`PHASES.md` format** — much shorter than a manifest, since phase
membership is now structural: it just records the phase order and which
one is active (optionally a short name/description per phase):

```markdown
# <Product> — Phases

## Phase 1 (active)

## Phase 2 (deferred)
```

Only one phase is ever **active** at a time — the one currently being
worked; this is what "the active phase" means for every phase-scoping
rule above, across whichever folders happen to be divided. Once at least
one folder is phase-divided, `/ideas-check` and `/ideas-fix` narrow their
undecided-feature and open-issue attention to the active phase only, per
folder independently as described above — deferred-phase items are
counted (so nothing looks silently forgotten) but not individually
surfaced or asked about every run — that's the whole point, not a gap.
When every divided folder's active-phase contents are fully resolved (no
`proposed`/`pending` features in `Features/Phase<active>/`, no
`outstanding` issues in `Issues/Phase<active>/`), `/ideas-phase` notices
on its next run and offers to promote the next phase to active — just
updating `PHASES.md`'s headers, never moving files, since nothing needs
to move when a phase is promoted — and never automatically, since
declaring a phase "done" is the human's call.

## Model policy for this skill

| Step | Model | Why |
|---|---|---|
| Reading notes / orchestrating / writing feature files | whatever the main session is running (typically Sonnet 5) | Mechanical once ambiguity is resolved |
| Problem statement (step 2) | **Fable** (Plan agent) | Highest-ambiguity step — raw notes, no structure yet |
| Candidate solutions (step 3) | **Fable** (Plan agent) | Needs genuinely distinct options, not one idea restated |
| Feature clustering (step 5) | **Fable** (Plan agent) | Deduplication and contradiction-detection benefit from the strongest reasoning available |
| Contradiction detection when ingesting new notes, or adjudicating `/ideas-check` issues | **Fable** (Plan agent) | Same reasoning as above — resolving genuine conflicts benefits from the strongest reasoning available |
| Drafting the problem statement and proposing solutions (`/ideas-problem`) | **Fable** (Plan agent), delegated via the `Agent` tool as a foreground subagent | Operationalizes steps 2 and 3 as a standalone command; same reasoning tier |
| Merge-or-new judgment and drafting (`/ideas-solution`) | **Fable** (Plan agent), delegated via the `Agent` tool as a foreground subagent | Telling a restated pitch apart from a genuinely new candidate is the same ambiguity-resolution work as step 3 |
| Clustering and drafting feature ideas (`/ideas-feature`) | **Fable** (Plan agent), delegated via the `Agent` tool as a foreground subagent | Operationalizes step 5's feature clustering as a standalone command; same reasoning tier |
| Narrating the product description (`/ideas-describe`) | **Fable** (Plan agent), delegated via the `Agent` tool as a foreground subagent | Synthesizing one coherent narrative out of a set of feature ideas is ambiguity-resolution work, same tier as the steps above |
| Proposing a starting phase-1 grouping (`/ideas-phase`) | **Fable** (Plan agent), delegated via the `Agent` tool as a foreground subagent, optional | Judging what's foundational vs. deferrable is ambiguity-resolution work; the human's own placement still wins over the suggestion |
| Candidate identification, drafting, and gap analysis (`/ideas-mine`) | **Fable** (Plan agent), delegated via the `Agent` tool as a foreground subagent | Same tier as `/ideas-feature`'s clustering — extracting one coherent idea from messy notes and spotting what it's missing are both judgment work |

This mirrors the model policy tracked in memory
(`model-selection-ideation-to-code-pipeline`, keyed to this skill under its
current name `ideas`): Fable for anything that resolves ambiguity or makes
a structural decision; the main session's model for everything else.

## Handoff

Once a feature idea is mature and the human wants to build it, it graduates
to the `specs` skill as a Build (`_Builds/<name>.build.spec.md`) — that's a
separate step, not part of this skill.
