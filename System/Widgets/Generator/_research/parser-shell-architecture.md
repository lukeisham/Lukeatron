### 1.5 Injection Order and Validation (assemble.py lines 98–253)

1. Load `shell.html` skeleton
2. Validate `config.yaml` against required fields (`validate_manifest()`)
3. Build `CONFIG` JS object from manifest (`build_config_js()`)
4. Compile `CONTENT` from `files.content` (JSON or Markdown outline)
5. Load and validate ENGINE/EXPLAINER source files — confirm exact export sets via regex:
   - `var ENGINE =` assignment present
   - `REQUIRED_ENGINE_KEYS = {"parse", "tokenize", "CLOSED"}` all present
   - `var EXPLAINER =` assignment present
   - `REQUIRED_EXPLAINER_KEYS = {"tables", "rules", "toMarkdown", "toText", "funcOf", "phraseOf", "clauseOf", "posShort", "needSpace"}` all present
6. Generate focus-level CSS from `CONFIG.levels` and `CONFIG.colours.palette`
7. Load cartridge `files.styles` CSS if present
8. Load sql.js vendor (WASM + JS) if needed (lexicon or spelling enabled)
9. Embed lexicon `.db` as base64 if `lexicon.enabled: true`
10. Wire spelling module (bundle + dictionary) if `spelling.enabled: true`
11. Wire MiniWiki module (bundle + articles) if `miniwiki.enabled: true`
12. Perform all string substitutions (23 replacements)
13. **Final validation pass:** regex-scan output for `__[A-Z_]+__` — any match = hard failure
14. Write output; log file size in MB

**Substitution is deterministic:** running the assembler twice on unchanged cartridge → byte-identical output.

## 3. ENGINE and EXPLAINER JS Contracts

### 3.1 ENGINE (FR-4)

**Export:** `var ENGINE = { parse, tokenize, CLOSED };`

```javascript
var ENGINE = (function () {
  function parse(text, selection) {
    // Required signature:
    // - text: string (input to parse)
    // - selection: undefined | { sweeps: { [id]: { on: bool, opposite: bool } } }
    //   (additive second arg; absent for cartridges without CONFIG.sweeps)
    // Returns: ParseResult (§4 below)
  }
  
  function tokenize(text) {
    // Returns: Token[]
    // Token shape: { i, text, start, end, isWord }
    // Used by: shell's word-count, spell-check timing
    // NOT used by spelling module (D-5) — spelling owns its own tokenizer
  }
  
  var CLOSED = {
    // Closed-class word lists; cartridge-owned
    // Shape: { className: { word: 1, word: 1, ... } }
    // Example: { determiner: { "the": 1, "a": 1 }, ... }
  };
  
  return { parse, tokenize, CLOSED };
})();
```

**Required exports (string-matched at build time):**
- `parse`
- `tokenize`
- `CLOSED`

### 3.2 EXPLAINER (FR-5, AD-1)

**Export:** `var EXPLAINER = { tables, rules, toMarkdown, toText, funcOf, phraseOf, clauseOf, posShort, needSpace };`

```javascript
var EXPLAINER = (function () {
  function tables(R) {
    // R: ParseResult
    // Returns: html string (rendered via innerHTML into #xtables)
    // Must produce a table for each clause's phrase structure
  }
  
  function rules(R) {
    // R: ParseResult
    // Returns: html string (rendered via innerHTML into #rules)
    // Deduplicated rule list extracted from findings
  }
  
  function toMarkdown(R) {
    // R: ParseResult
    // Returns: markdown string (copied to clipboard)
  }
  
  function toText(R) {
    // R: ParseResult
    // Returns: plain text string (copied to clipboard)
  }
  
  function funcOf(R, tokenIndex) {
    // R: ParseResult
    // tokenIndex: number (index into R._toks)
    // Returns: string (e.g., "subject", "predicate")
    // Used by: hover text, right-click context menu
  }
  
  function phraseOf(R, tokenIndex) {
    // R: ParseResult
    // tokenIndex: number
    // Returns: Span | null
    // Span.kind should be 'phrase' or 'phrase-inner'
    // Used by: render loop to wrap tokens in <span class="ph">
  }
  
  function clauseOf(R, tokenIndex) {
    // R: ParseResult
    // tokenIndex: number
    // Returns: Span | null
    // Span.kind should be 'clause'
    // Used by: hover text, hue assignment
  }
  
  function posShort(token) {
    // token: Token (from R._toks[i])
    // Returns: string (e.g., "N", "V", "Adj")
    // Used by: word render at word-focus level (.pos display)
    // Required move (AD-1): shell NEVER re-implements this locally
  }
  
  function needSpace(a, b) {
    // a, b: Token
    // Returns: boolean (should a space render between a and b?)
    // Example: false between word and punctuation in English
    // Required move (AD-1): shell NEVER re-implements this locally
  }
  
  return { tables, rules, toMarkdown, toText, funcOf, phraseOf, clauseOf, posShort, needSpace };
})();
```

**Required exports (string-matched at build time):**
- `tables`
- `rules`
- `toMarkdown`
- `toText`
- `funcOf`
- `phraseOf`
- `clauseOf`
- `posShort`
- `needSpace`

## 6. Focus-Level CSS Generation

### 6.1 Generic Template Algorithm (AD-2)

**Source:** `assemble.py` function `generate_focus_css(levels, palette)` (lines 545–602)

**Input:**
- `levels: list[str]` — ordered coarse→fine level names from `CONFIG.levels`
  - Example: `["sentential", "clausal", "phrasal", "lexical"]`
- `palette: list[dict]` — hue definitions from `CONFIG.colours.palette`
  - Each hue: `{h50, h100, h600, h800, hf, name}`

**Algorithm:**

```python
n = len(levels)
cl_home = 1 if n > 1 else 0      # Clause home: index 1, or 0 if only 1 level
ph_home = 2 if n > 2 else -1     # Phrase home: index 2, or -1 if < 3 levels (no rule emitted)
w_home = n - 1                    # Word home: always the last level

for p, level in enumerate(levels):
    selector = f"#stage.v-{level}"
    
    # Clause (.cl) rule: different at each position
    if p == cl_home:
        # Full intensity, show label
        emit: {selector} .cl{background:var(--h50);color:var(--h800);}
        emit: {selector} .lbl{display:inline-block;background:var(--h100);color:var(--h800);}
    elif p == 0:
        # Boundary treatment (coarsest level)
        emit: {selector} .cl{background:var(--hf);border-left:3px solid var(--h600);...;}
    else:
        # Middle levels: faded
        emit: {selector} .cl{background:var(--hf);}
    
    # Phrase (.ph) rule: only at phrase home
    if p == ph_home:
        emit: {selector} .ph{background:var(--h100);color:var(--h800);padding:1px 4px;}
    
    # Word (.w) rule: only at word home
    if p == w_home:
        emit: {selector} .w{background:var(--h100);color:var(--h800);...;}
        emit: {selector} .pos{font-size:11px;...;}  # POS label
```

**Output:** Multi-line CSS string injected into shell.html `<style>` block after `__SHELL_CSS__` and before `__CARTRIDGE_CSS__`.

### 6.2 Grammar Example (n=4)

Input: `["sentential", "clausal", "phrasal", "lexical"]`

```css

#stage.clausal .cl{background:var(--h50);color:var(--h800);}
```

1. **Blob + URL.createObjectURL (primary):** Works from `file://`, keeps `document.write` out of play

## 9. Input-Analysis-Specific vs. Generator-Mode Architecture

### 9.1 Current Parser Shell: Input-Analysis Workflow

```
User Input → Parse → Render → Display → Explain
   #input    ENGINE  Markup   Hover     EXPLAINER
```

**What is tightly coupled to text input:**

1. **User input area** (`#input` contenteditable)
2. **Word counter** (`wordCount()` calls ENGINE.tokenize())
3. **Spell-check timing** (debounced on input event)
4. **Over-cap gate** (blocks parsing, shows warning)
5. **Parse button** → ENGINE.parse(text)
6. **Focus-level rendering** (level selector switches `.v-<level>` CSS class)
7. **Hover/context menu** (reads from `R`, not input)

### 9.2 Generator Mode: What Would Need Replacing

**For a "generate-then-display" widget (e.g., `RandomSentenceGenerator`):**

| Component | Current | Generator Replacement |
|-----------|---------|----------------------|
| Input area | `#input` contenteditable | Hidden or repurposed |
| Word counter | Live, updates on keystroke | Static, shows generator output size |
| Spell-check | Enabled on input | Could stay (checks generated text) |
| Over-cap gate | Blocks parsing if too long | N/A (output size controlled at generation) |
| Parse trigger | Parse button → ENGINE.parse(text) | **Generate button** → ENGINE.parse(generatedContent) |
| Content source | Text typed/pasted by user | **Baked-in JSON/lookup** or **API call** (for GENERATOR mode) |
| Explain gate | Manual click on "Explain" button | Same (no change) |
| Export buttons | Copy/PDF of Explainer | Same (no change) |
| Focus levels | Same level selector, CSS rules | Same (no change) |
| Hover/context | Same (reads from ParseResult) | Same (no change) |

### 9.3 Shell Modifications Needed for Generator Mode

**Minimal path — only touch ui.js, not the shell skeleton:**

```javascript
// REPLACE: parseNow() and input/word-count handling

// OLD (input-analysis):
function parseNow() {
  var text = getInputText();
  if (!text) return;
  R = ENGINE.parse(text, readSweepSelection());
  render();
}

// NEW (generator):
function generateAndParse() {
  // Call generator API or lookup (config-defined)
  var generated = ENGINE.generate();  // OR: getFromBakedInContent()
  R = ENGINE.parse(generated, readSweepSelection());
  render();
}

// UPDATE button wiring:
$("btnParse").textContent = "Generate";  // Rename button
$("btnParse").addEventListener("click", generateAndParse);  // Re-wire handler

// Hide/disable word counter and spell-check inputs
$("input").style.display = "none";      // Hide input area
$("spellLabel").style.display = "none"; // Hide spell-check checkbox
$("wcount").textContent = "...";        // Static, no live updates
```

**No other shell layer changes needed:**

- Render loop, focus-level CSS, hover, explain, export → unchanged
- CONFIG contract → unchanged (add a `generator` section if needed, but not required)
- EXPLAINER exports → unchanged
- ParseResult schema → unchanged

### 9.4 Generator-Specific Additions (CONFIG)

Example extension for generator mode:

```yaml
generator:          # NEW, optional
  enabled: true
  mode: "api" | "baked" | "random"
  
  # If mode: "api"
  endpoint: "https://..."
  
  # If mode: "baked"
  contentFile: "examples.json"
  
  # If mode: "random"
  templates: [...]
  
  # Interactive features
  interactions:
    - id: "reveal-clue"
      label: "Reveal clue"
      action: "click"
    - id: "check-answer"
      label: "Check answer"
      action: "click"
```

**But this is NOT required** for a working generator parser — add it only if the cartridge needs configuration-level control. A generator can be hard-coded in its own ENGINE.

### 9.5 What Stays Input-Analysis-Specific

**These elements are INHERENTLY analysis-driven and cannot easily transfer to generation:**

1. **Live spell-check on user input** — still useful for generated text, but timing changes
2. **Input validation** (cap gate) — becomes output validation (generation must respect cap)
3. **Keystroke debouncing** — no keystroke in generator mode
4. **Real-time word counter** — becomes static "generation produced N words"

**These are UNCHANGED and work as-is:**

1. Focus-level rendering and CSS
2. Hover tooltips and context menus
3. Explainer rendering (tables, rules, export)
4. Interaction layer (buttons, keybindings)

## 12. Risk: Underscore-Prefixed Private Coupling (OQ-2)

**Status:** Documented as unfinished business in spec.

`R._toks` and `R._clauses` are underscore-prefixed (private-by-convention) but **required** for render loop to function.

**Current usage (ui.js lines 208–239):**

```javascript
var toks = R._toks;           // Line 208
var clauses = R._clauses;     // Line 208
// ...loop reads both directly
```

**Ideal future (not yet implemented):** Expose accessor via EXPLAINER

```javascript
var clauses = EXPLAINER.clauseSpans(R);  // Mediated, not underscore-access
var toks = EXPLAINER.tokens(R);          // Mediated
```

**Impact on generator mode:** None — both input-analysis and generation produce ParseResult with the same schema, so no special handling needed.
